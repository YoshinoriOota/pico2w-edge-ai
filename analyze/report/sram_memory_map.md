# RP2350 SRAM (520KB) メモリマップ設計

## 1. 前提

- RP2350のSRAMは合計 **520KB (532,480 bytes)**。
  内部は10バンク構成: `SRAM0`〜`SRAM7`(各64KB = 512KB) + `SRAM8`〜`SRAM9`(各4KB = 8KB)。
  ベースアドレスは `0x20000000`。
- 用途は以下4区分 + システム領域(.data/.bss)で構成する。
  1. OV7670フレームバッファ (QQVGA 160x120x2byte)
  2. WiFi/lwIPバッファ
  3. DNNRT中間バッファ
  4. スタック・ヒープ
- 本設計は「予算(バイト数の割り当て)」であり、リンカスクリプトで厳密にアドレス固定するものではない。
  各領域は静的配列(`.bss`)または専用アロケータ(後述)として実装し、
  リンカが標準の `memmap_default.ld` に従って単一RAM領域内に自動配置する。
  バンク単位での配置を厳密に固定したい場合のみ、リンカスクリプトのセクション指定が必要になる(7章参照)。

## 3. ① OV7670フレームバッファ (75.0KB)

### サイズ根拠
- QQVGA = 160 × 120 = 19,200 pixel
- RGB565 / YUV422 いずれも **2 byte/pixel**
- 1フレーム = 19,200 × 2 = **38,400 bytes (37.5KB)**

### ダブルバッファが必要な理由
- PIO + DMAはCPUと非同期に常時キャプチャを継続する。
- シングルバッファだと、AI推論やWiFi送信でフレームを読み出している最中に
  DMAが同じバッファへ次フレームを上書きし、**ティアリング**(画像の上下で
  異なるフレームが混在する)が発生し得る。
- ピンポン(double)バッファ構成にし、DMAが書き込み中のバッファと
  アプリが読み出し中のバッファを分離する。
- → 38,400 × 2 = **76,800 bytes ≈ 75.0KB**

### 削減オプション(参考)
- VSYNC割り込みでDMAを一時停止し、フレーム消費完了を待ってから再開する
  「シングルバッファ+同期」方式なら37.5KBで済む。ただしフレームレートが
  処理時間(WiFi送信+推論)に律速される。SRAMが逼迫した場合の代替案。

## 4. ③ DNNRT中間バッファ (100.0KB)

### 割当の考え方
nnabla-c-runtimeは `rt_initialize_context()` 実行時、NNB内の
`memory.buffers` リスト(変数のライフタイム解析済み・**バッファ再利用込み**)
に従って `rt_variable_malloc_func` でバッファを確保する
([build_report.md](build_report.md) 6.1節参照)。
そのため必要量はモデル構成に強く依存する。

### 試算(QQVGA画像をリサイズした小規模CNNを想定)

| レイヤ | 出力形状 | 要素数 |
|---|---|---:|
| 入力 (グレースケールにリサイズ) | 48×48×1 | 2,304 |
| Conv1 (8ch, 3x3, same) | 48×48×8 | 18,432 |
| Pool1 (2x2) | 24×24×8 | 4,608 |
| Conv2 (16ch, 3x3, same) | 24×24×16 | 9,216 |
| Pool2 (2x2) | 12×12×16 | 2,304 |
| FC層 | - | 数百 |

- **FIXED8 (INT8量子化)** の場合: 最大バッファ(Conv1出力 18,432B)を中心に
  ライフタイム再利用後の合計は概ね **30KB程度**
- **FLOAT32** の場合: 上記の4倍 ≈ **120KB**

### 100KBとした理由
- 上記試算のFLOAT32ケース(~120KB)に近いが、INT8量子化を基本方針とすれば
  実使用量は30〜50KB程度に収まり、入力解像度を64×64程度まで上げる余地や
  レイヤ追加の余地を残せる。
- **実装方針**: `rt_set_variable_malloc()` / `rt_set_variable_free()` で
  この100KB静的配列上の専用バンプアロケータを登録し、汎用ヒープ(⑤)とは
  完全に分離する。これによりlwIPの頻繁なalloc/freeとの間でヒープが
  断片化し、DNNRTの大きな連続バッファ確保が失敗するリスクを排除する。

## 5. ④ WiFi/lwIPバッファ (48.0KB)

CLAUDE.mdの設計方針(UDP unicast、RAWフレームデータ送信)に基づき、
**TCPは無効化(`LWIP_TCP=0`)** してTCP関連バッファを削減する前提。

| 内訳 | サイズ | 根拠 |
|---|---:|---|
| pbufプール (`PBUF_POOL_SIZE=16` × `PBUF_POOL_BUFSIZE≈1564B`) | ~24.4KB | フレーム(38.4KB)はMTU 1500Bで約26パケットに分割送信。送信用pbufは都度確保・解放されるため、同時飛行数程度のプール数(16)で足りる |
| lwIPヒープ (`MEM_SIZE=4000`) | ~3.9KB | UDP PCB・ARPテーブル等の制御構造体 |
| cyw43ドライバ内部バッファ (SPI/SDIOバスIF送受信・イベントキュー) | ~8.0KB | CYW43439とのバス通信用固定バッファ |
| ARPキュー・その他制御構造体 | ~3.0KB | `MEMP_NUM_ARP_QUEUE`等 |
| **小計** | **~39.3KB** | |
| マージン | ~8.7KB | 将来のTCP有効化・再送バッファ等への余裕 |
| **合計** | **48.0KB** | |

## 6. ⑤⑥ スタック・ヒープ (合計 277.0KB = ⑤261.0KB + ⑥16.0KB)

### ⑥ スタック: 16.0KB (Core0 8KB + Core1 8KB)
- Pico SDKのデフォルト `PICO_STACK_SIZE` は0x800(2KB)/コアだが、
  以下を考慮し**コアあたり8KB**を確保:
  - DNNRTの畳み込み処理のネストしたループ・関数呼び出し
  - `printf` の浮動小数点フォーマット処理(スタック消費が大きい)
  - lwIPのコールバックチェーン(割り込みコンテキストからのコールバック)
- Core1未使用の構成であれば8KBのみで良いが、将来Core1へカメラ
  キャプチャ処理やWiFi送信処理をオフロードする可能性を見込み、
  2コア分(16KB)を予約。

### ⑤ 汎用ヒープ・予備: ~261.0KB (50.2%)
- 上記①〜④, ⑥を確保した残り全て。
- 用途:
  - lwIPの動的割当(`MEM_LIBC_MALLOC=1`の場合のmalloc経由領域。④で
    `MEM_SIZE`として確保した分を超える一時割当)
  - アプリケーションの一時バッファ(JPEGエンコード、ログバッファ等の将来拡張)
  - DNNRTモデル切替・大型化時の③アリーナ拡張余地
  - 安全マージン(OOM回避)
- **設計段階で50%以上を未割当のまま残す**ことで、書籍の「検討中」段階の
  AIパイプライン方式(DNNRT/TFLite Micro)のどちらを採用しても、
  またモデルサイズが想定より大きくなっても吸収できる余裕を確保している。

## 7. (補足) SRAMバンクとの対応

RP2350は `SRAM0`〜`SRAM7`(各64KB)+ `SRAM8`〜`SRAM9`(各4KB)の
クロスバー接続構成。①〜⑥を上記オフセット順に並べると、各領域は概ね
以下のバンクにまたがる。

| 領域 | またがるバンク |
|---|---|
| ① .data/.bss | SRAM0 |
| ② フレームバッファ | SRAM0-1 |
| ③ DNNRTアリーナ | SRAM1-3 |
| ④ WiFi/lwIPバッファ | SRAM3 |
| ⑤ 汎用ヒープ | SRAM3-7 |
| ⑥ スタック | SRAM7, SRAM8, SRAM9 |

RP2350のクロスバーは複数バスマスタ(CPU/DMA/DMA)から異なるバンクへの
同時アクセスを基本的にノンブロッキングで処理できるため、
「②フレームバッファへのDMA書き込み」と「③DNNRTアリーナへのCPU演算アクセス」が
別バンク(SRAM0-1 / SRAM1-3)に分かれている本マップは、バンク競合の観点でも
都合が良い構成になっている。

ただし、上記のバンク対応はリンカが`.bss`領域を確保した結果の**目安**であり、
厳密に固定したい場合(例: フレームバッファをSRAM0に固定してDMAとCPUの
バンク競合を完全に避けたい等)は、カスタムリンカスクリプトで
`__attribute__((section(".framebuf")))` のような専用セクションを
定義し、`MEMORY` 領域を分割する必要がある。本設計の段階では
予算配分(バイト数)の決定を優先し、バンク固定は実装フェーズの
最適化課題として残す。
