# 第3章 Raspberry Pi Pico 2 W を知る — 520KB の土地に AI を住まわせる

カメラの配線という最初の山場（第4章）に挑む前に、この章では舞台となる基板 — Raspberry Pi Pico 2 W の中身を頭に入れます。手を動かす場面は少なめですが、ここで作る「土地勘」が後のすべての章で効いてきます。テーマは3つ。**メモリはどれだけ使えるのか**（3.1）、**Python でカメラの高速信号を受けられる秘密は何か**（3.2〜3.3）、そして**電気はどこで消えるのか**（3.4）です。

## 3.1 RP2350 の実力 — 520KB SRAM と MicroPython ヒープの関係

### 名刺の半分に載っているもの

Pico 2 W の心臓部は、Raspberry Pi 財団が自社設計したマイコンチップ **RP2350** です。主なスペックを、旧世代と並べて見てみましょう。

| | Pico（無印） | Pico 2 | **Pico 2 W（本書）** |
|---|---|---|---|
| チップ | RP2040 | RP2350 | RP2350 |
| CPU | Cortex-M0+ ×2 / 133MHz | Cortex-M33 ×2 / 150MHz | Cortex-M33 ×2 / 150MHz |
| SRAM | 264KB | 520KB | **520KB** |
| フラッシュ | 2MB | 4MB | **4MB** |
| PIO | 2ブロック（8SM） | 3ブロック（12SM） | **3ブロック（12SM）** |
| Wi-Fi | なし | なし | **あり（CYW43439）** |
| 参考価格 | 約800円 | 約1,000円 | 約1,500円 |

本書が Pico 2 W を指定する理由がこの表に詰まっています。**SRAM 520KB**（旧型の約2倍 — AI モデルとカメラ画像を同居させる余裕）、**PIO が3ブロック**（カメラ取り込みに使う秘密兵器。3.2 で説明します）、そして**Wi-Fi**（通知に必須）。逆に言えば、無印 Pico や Pico 2 では本書の作例は動きません。購入時は「2」と「W」の両方が付いていることを確認してください。

ちなみに RP2350 にはもうひとつ面白い特徴があります。ARM Cortex-M33 のほかに RISC-V コア（Hazard3）も内蔵していて、起動時にどちらのアーキテクチャで動くか選べるのです。本書では標準の ARM 側しか使いませんが、1つのチップに2種類の CPU が同居している — そんな遊び心のあるチップだと知っておくと愛着が湧きます。

### 520KB のうち、実際に使えるのは何 KB か

さて、カタログの「SRAM 520KB」を鵜呑みにしてはいけません。MicroPython という OS 相当のソフトウェアが自分の作業領域を確保するため、私たちの Python プログラムが使える **ヒープ**（動的メモリ）はそれより少なくなります。実際に測ってみましょう。REPL で：

```python
>>> import gc
>>> gc.collect()
>>> gc.mem_free()
446112
```

本書の配布ファームウェアでは、起動直後の空きヒープは**約 446KB** です（数値は環境で多少前後します）。520KB との差の大半は、MicroPython 本体と Wi-Fi ドライバの取り分です。

この 446KB という土地に、本書の最終形では次の住人が入居します。

```text
  起動直後の空きヒープ 約446KB
  ├─ カメラのフレームバッファ(160×120 RGB565) ····· 38.4KB
  ├─ AIモデル(model.nnb)本体 ······················ 約14KB
  ├─ 推論の中間バッファ+作業領域 ···················· 約25KB
  └─ 残り(Wi-Fi処理・自分のコード・余裕) ·········· 約369KB ← まだ7割空いている
```

「マイコンで AI」と聞いて想像するカツカツの綱渡りとは、だいぶ印象が違うのではないでしょうか。これは偶然ではなく設計の結果です — 入力を 28×28 に絞り、モデルを 14KB に抑える判断（第8章）の見返りが、この余裕なのです。逆に、調子に乗って入力画像を大きくするとこの図は一気に崩れます。**新しい機能を足すときは `gc.mem_free()` で家賃を確認する** — この習慣を本書では一貫して守ります。

### ヒープとフラッシュ — 「机」と「本棚」

もうひとつ、混同しやすい区別を押さえておきます。SRAM（ヒープ）が計算に使う「机の広さ」だとすると、4MB のフラッシュは「本棚」です。第2章で main.py を保存した場所、そして第9章で model.nnb を置く場所は本棚（フラッシュ）で、電源を切っても消えません。机は広くありませんが、本棚には余裕があります。AI モデルは普段は本棚に眠っていて、推論のときだけ机に広げられる — この関係を覚えておくと、第9章の話がすっと入ります。

## 3.2 PIO（Programmable I/O）とは何か — Python から使えるハードウェア支援

### Python は「速さ」で勝負できない

第4章で扱う OV7670 カメラは、画素データを **1秒あたり約100万バイト**のペースで送りつけてきます。1バイトあたり約1マイクロ秒。一方、MicroPython のループが1周するのにかかる時間は、どんなに切り詰めても数マイクロ秒です。つまり：

```python
while True:
    b = read_pixel()   # ← この1周が終わる前に、次のデータが来てしまう
    buf[i] = b
```

**Python のループでは、原理的に間に合いません。** ではどうするか。世間の答えは「そこだけ C で書く」ですが、本書は C を書かない約束です。ここで登場するのが RP2350 の秘密兵器、**PIO（Programmable I/O）**です。

### 本社と現場作業員

PIO は、CPU とは独立に動く小さな専用プロセッサです。RP2350 には PIO ブロックが3つあり、各ブロックに **ステートマシン**と呼ばれる実行ユニットが4基、計12基入っています。それぞれが GPIO ピンを直接見張り、CPU に一切頼らずに信号を読み書きできます。

会社にたとえると、CPU（MicroPython）は本社の企画部です。賢くて何でもできますが、現場に張り付いて1マイクロ秒ごとの検品はできません。PIO は現場の検品作業員です。できる作業は9種類の単純命令だけ。そのかわり、**1命令をきっかり1クロック（150MHz なら約6.7ナノ秒）で、脇目もふらず実行し続けます。**

さらにもう一人、**DMA（Direct Memory Access）**という運搬係がいます。PIO が検品した荷物（データ）をメモリの倉庫まで運ぶベルトコンベアです。これも CPU の手を借りません。

```text
   OV7670 ──信号──→ [PIO] ──── [DMA] ────→ メモリ(フレームバッファ)
                    検品係      ベルトコンベア
                      ↑ 立ち上がりを待って8bit拾う、を百万回/秒
                                            ↑ 拾った端から倉庫へ直行
   [CPU/MicroPython] ······ その間、昼寝していてもよい(企画部)
```

第4章では、MicroPython が「作業手順書（PIO プログラム）を書いて渡し、開始の号令をかけ、あとは待つ」だけでカメラ画像が丸ごとメモリに現れる様子を実際に見ます。**Python の書きやすさと、ハードウェアの速さの両立** — 本書の技術構成でいちばん痛快な部分です。

### 手順書は Python の中に書ける

PIO の手順書（プログラム）は専用のアセンブリ言語で書きますが、MicroPython にはそれを Python コードの中に埋め込む仕組みが用意されています。雰囲気だけ先取りしてみましょう。

```python
import rp2

@rp2.asm_pio(set_init=rp2.PIO.OUT_LOW)
def blink():             # ← 中身は Python ではなく PIO アセンブリ
    set(pins, 1) [31]    # ピンを HIGH にして 31クロック待つ
    nop()        [31]
    set(pins, 0) [31]    # ピンを LOW にして 31クロック待つ
    nop()        [31]
```

`@rp2.asm_pio` という飾り（デコレータ）が付いた関数の中身は、PIO の命令として翻訳されます。この4行を `freq=2000` で動かせば、CPU の関与ゼロで LED が点滅し続けます（GP15 などに LED を配線すれば実際に試せます。ちなみに基板上の LED では試せません — その理由は次の 3.3 で明かします）。

ひとつだけ制約を覚えておいてください。手順書は **1ブロックあたり32命令まで**しか置けません。豪華な処理は書けない、だからこそ速い — それが PIO です。第4章のカメラ取り込みプログラムは11命令。制約の中に収める設計も含めて楽しんでいきましょう。

## 3.3 Wi-Fi（CYW43439）の基本

### 無線は「別の住人」

Pico 2 W の Wi-Fi は、RP2350 自身の機能ではありません。基板の端に載っているもう一つのチップ — Infineon 製 **CYW43439** が担当しています。RP2350 とは社内 LAN（SPI 接続）でつながった、いわば「別の住人」です。

この事実は、2つの場面で顔を出します。

第一に、**基板上の LED**。第2章で `Pin("LED")` と名前指定した理由がこれです。Pico 2 W の LED は RP2350 の GPIO ではなく、**CYW43439 側のピン**にぶら下がっています。番号で指定できないので名前で呼ぶのです（PIO で基板 LED を点滅できないのも同じ理由 — PIO が触れるのは RP2350 側のピンだけです）。

第二に、**電力**。別の住人ですから、独自に電気を使います。これが後で大問題になるのですが、まずは使い方から見ましょう。

### つないで、確かめる

Wi-Fi 接続は `network` モジュールで行います。REPL で試してみてください（SSID とパスワードはご自宅のものに置き換えます）。

```python
>>> import network
>>> wlan = network.WLAN(network.STA_IF)   # 子機(ステーション)モード
>>> wlan.active(True)                     # CYW43439 に電源投入
>>> wlan.connect("あなたのSSID", "パスワード")
>>> wlan.isconnected()                    # 少し待ってから
True
>>> wlan.ifconfig()[0]                    # 割り当てられたIPアドレス
'192.168.1.53'
```

`True` と IP アドレスが返れば、あなたの Pico はいまインターネットの末端にいます。2.4GHz 帯のみ対応（5GHz の SSID には接続できません）なので、つながらないときはまずそこを確認してください。

本書での Wi-Fi の使い道は「推論結果の通知」だけです。具体的な送信コードは第10章・第11章で書きますが、方針だけ先に言っておくと **UDP でごく短いメッセージを投げる**という最小構成にします。数十バイトの結果を送るのに、重たい仕組みは要りません。

### 使い終わったら、必ず消灯する

そして予告した電力の話です。CYW43439 は、接続を維持しているだけで無視できない電流を消費します。さらに厄介なことに、**RP2350 本体をスリープさせても CYW43439 は勝手には眠りません。** 別の住人だからです。

筆者の実測では、Wi-Fi チップを止め忘れたまま本体をスリープさせたところ、消費電流は約29mA — なんと**通常のアイドル状態（約18mA）より高い**という本末転倒な結果になりました。正しく `wlan.active(False)` で消灯してからスリープすれば約10mA。この一行の有無で、電池寿命が倍以上変わります。

```python
>>> wlan.active(False)   # 使い終わったら必ず。これを忘れると第10章で泣きます
```

「Wi-Fi は送るときだけ点け、送ったら必ず消す」— 本書の省電力設計の合言葉として、ここで胸に刻んでおいてください（第10章で実測データとともに再登場します）。

## 3.4 消費電流の基礎知識 — 動作時・スリープ時・Wi-Fi送信時で何が違うか

### 電池は「電流×時間」の貯金箱

AI カメラの本なのに、なぜ電流の節がこんなに手前にあるのか。本書のゴールが「電池で動く」だからです。そして電池設計の算数は、拍子抜けするほど単純です。

単3電池2本の容量はおよそ **2000mAh**（ミリアンペア時）。これは「2000mA を1時間」でも「20mA を100時間」でも引き出せる貯金箱だと思ってください。使える時間は：

```text
  動作時間[時間] = 電池容量[mAh] ÷ 平均消費電流[mA]
```

割り算1回。問題は、分母の「平均消費電流」をどう小さくするかに尽きます。

### 実測で見る「電気の使い道」

では本書の装置は、状態ごとにどれだけ電気を使うのか。筆者が実測した値を先にお見せします（USB 給電経路での測定値。厳密な測り方と電池駆動での値は第10章で扱います）。

| 状態 | 消費電流（実測） | 倍率 |
|---|---|---|
| deepsleep（深い眠り） | 6.0 mA | 1.0 |
| lightsleep（浅い眠り、Wi-Fi 停止後） | 10.1 mA | 1.7 |
| アイドル（起きて待機） | 17.7 mA | 3.0 |
| 撮影＋AI推論の実行中 | 30.5 mA | 5.1 |
| Wi-Fi 動作中（接続処理・送信） | 42.0 mA | 7.0 |

この表から2つのことが読み取れます。

**その1：最大でも42mA — 全部が「小さい」世界。** 家庭の LED 電球1個が数百mA相当ですから、この装置はフルパワーでもその1割以下です。マイコンの世界の省エネぶりがわかります。

**その2：それでも7倍の差がある。** そして電池寿命を決めるのは、この差の使い方です。

### 「ずっと起きている」は許されない

試しに、スリープを使わずアイドルのまま放置する設計を考えてみます。2000mAh ÷ 17.7mA ≈ 113時間 — **たった4.7日**で電池切れです。撮影も通知もしていないのに、です。

では本書の設計 — 10分に1回だけ起きて、撮影・推論（約1秒、30.5mA）と必要なら通知（数秒、42mA）を済ませ、残りを deepsleep（6.0mA）で過ごす間欠動作ならどうか。活動時間が短すぎて平均への影響はごくわずかで、平均消費電流は約6.4mA。2000 ÷ 6.4 ≈ 312時間 ≈ **約13日**。同じ電池で寿命が3倍近く伸びます。

```text
  ずっと起きている設計:  ████████████████████ 17.7mA → 約4.7日
  間欠動作の設計:        ███████ 平均6.4mA        → 約13日
                         ↑ ほぼ deepsleep の 6.0mA で決まる
```

お気づきでしょうか。間欠動作の平均 6.4mA のうち 6.0mA は deepsleep の取り分です。つまりこの装置の電池寿命は、派手な推論やWi-Fiではなく、**眠りの深さでほぼ決まっている**のです。第1章で「いかに深く静かに眠れるか」と書いた意味が、数字でつながったはずです。

なお、勘のいい読者は「deepsleep の 6mA、もっと下げられないのか」と思ったかもしれません。いい質問です — 下げられます。ただしそこには MicroPython の限界と、それを外部回路で突破する話（第10章末の「さらに攻める」）が待っています。楽しみにしていてください。
