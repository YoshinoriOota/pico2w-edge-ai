# 第8章 モデルをマイコンサイズにする — 310KB の LeNet と 14KB の実用モデル

第7章までで、自分のデータで学習する準備が整いました。この章のテーマは**モデルのダイエット**です。といっても、やみくもに削るのではありません。NNC の画面に出ている数字から「どこが重いのか」を突き止め、狙って削る — 家計簿をつけてから節約する、という章です。

先に今章の結論を実測で示します。筆者が第6章の LeNet（Fashion-MNIST 学習済み）をそのまま Pico に載せてみた結果と、本書の最終モデルの比較です。

| | LeNet をそのまま | 本書の設計（ダイエット後） |
|---|---|---|
| model.nnb のサイズ | 316,936 byte（約310KB） | 13,964 byte（約14KB） |
| ロード後のヒープ残 | **69KB** | **369KB** |
| 推論1回 | 299 ms | 90 ms |

注目すべきは推論時間ではありません — 299ms でも間欠動作カメラには十分です。問題は**ヒープ残 69KB** の方です。カメラのフレームバッファ（38.4KB）を足すと残りわずか30KB。Wi-Fi と自分のコードの分を考えると、いつ MemoryError が出てもおかしくない綱渡りです。LeNet は「動くけれど、同居人を追い出してしまう」— これがダイエットの動機です。

## 8.1 NNC の統計情報でサイズを見積もる

### CostParameter — 「重さ」はエクスポート前にわかる

第6章の編集タブで、画面右にこんな数字が出ていたのを覚えているでしょうか。

```text
  統計情報 (LeNet の例)
  CostParameter    78,810     ← パラメータ(重み)の総数
  CostMultiplyAdd  802,876    ← 推論1回あたりの積和演算の回数
```

この2つが、モデルの「体重計」です。まず **CostParameter**。第5章で学んだとおり、モデルの実体はダイヤル（重み）の集合で、1個のダイヤルは float32 = 4バイトです。つまり：

```text
  model.nnb のサイズ ≒ CostParameter × 4 バイト
  LeNet: 78,810 × 4 = 315,240 バイト  (実際のエクスポート結果: 316,936 バイト)
```

差の約1,700バイトはネットワーク構造の記述などのヘッダ分です。**エクスポートするまでもなく、編集タブの数字だけで .nnb のサイズは読める** — これが体重計の使い方その1です。

もうひとつの **CostMultiplyAdd** は速度の目安です。LeNet は推論1回に約80万回の積和演算を行い、Pico 実機では 299ms でした。本書の用途では速度は問題になりにくいので、まずは CostParameter を見る習慣をつけてください。

### メモリの家計簿 — .nnb だけでは終わらない

Pico 上でモデルが消費するのは .nnb 本体だけではありません。実測から逆算した LeNet の「入居費用」の全体像はこうです。

```text
  起動直後のヒープ         約451KB
  ├─ model.nnb 本体       317KB   ← CostParameter × 4B + ヘッダ
  ├─ 中間バッファ+作業領域  約65KB   ← 層の途中結果 (特徴マップ) の置き場
  └─ 残り                  69KB   ← ここにカメラ38KB・Wi-Fi・コードが同居できるか?
```

中間バッファは「各層の出力（特徴マップ）を一時的に置く場所」で、こちらは**フィルタ枚数と画像サイズ**に比例します。目安としては、いちばん大きな特徴マップ（LeNet なら1段目 Conv 出力の 16×22×22 ≒ 31KB）の数倍を見込んでおくと安全です。

## 8.2 入力解像度・チャネル数・層数を削る設計指針

### 犯人捜し — LeNet はどこが重いのか

削る前に、78,810 個のダイヤルが**どの層に**いるのかを調べます。第5章のパラメータ数の計算（重み＝入力×出力のかけ算＋下駄）を各層に当てはめるだけです。

| 層 | 計算 | パラメータ数 | 割合 |
|---|---|---|---|
| Convolution（7×7, 16枚） | 16×1×49 + 16 | 800 | 1.0% |
| Convolution_2（3×3, 30枚） | 30×16×9 + 30 | 4,350 | 5.5% |
| **Affine（480→150）** | **480×150 + 150** | **72,150** | **91.5%** |
| Affine_2（150→10） | 150×10 + 10 | 1,510 | 1.9% |
| 合計 | | **78,810** | （統計情報と一致!） |

一目瞭然です。**LeNet の重さの9割は、たった1つの Affine（全結合）層に集中しています。** 第5章で「畳み込みは倹約、全結合は大食い」と学んだことが、実物の家計簿で裏付けられました。畳み込み2層は合わせても6.5% — 捜査部隊は軽く、裁判所が重いのです。

### 削る優先順位

犯人がわかれば、対策は自然に決まります。効き目の大きい順に：

**① Affine の入口を小さくする（最重要）。** Affine のパラメータ数は「入口×出口」の掛け算なので、入口（＝直前の特徴マップの総画素数）を半分にすればパラメータも半分です。手段は MaxPooling を1段増やすこと — LeNet の入口 480（30×4×4）が、Pool をもう1段通せば 4分の1 になります。「**Affine に渡す前に、Pool で絞る**」が鉄則です。

**② Affine の出口（中間ニューロン数）を減らす。** LeNet の150人の陪審員は、10クラスの Fashion-MNIST 向けの陣容です。あなたの2〜3クラス問題なら 16〜32人で十分です。

**③ フィルタ枚数（チャネル数）を減らす。** 16枚・30枚 → 8枚・16枚に半減すると、畳み込み層のパラメータと**中間バッファの両方**が減ります。中間バッファに効くのはこの手だけなので、メモリの家計簿と相談しながら調整します。

**④ 入力解像度は…もう十分小さい。** 28×28 はすでにマイコン向けの解像度です。本書ではこれ以上削りません（削るなら 24×24 程度までが実用限界でしょう）。

この指針で組み直したのが本書の最終モデルです。Conv 2段（8枚・16枚）＋深めの Pool ＋小さな Affine という構成で、**パラメータ約3,500個 ≒ .nnb 14KB**。章冒頭の表のとおり、ヒープ残 369KB という広々とした家計を実現します。具体的なレイヤー構成は第9章で、実データの学習と合わせて組み立てます。

### 精度は落ちないのか

落ちます — ただし、思ったよりずっと少なく。Fashion-MNIST のような10クラス問題では数ポイントの差が出ますが、**定点・2クラス・同一環境**というあなたの問題（第7章の題材選定を思い出してください）では、3,500個のダイヤルでも過剰なくらいです。むしろパラメータが少ないほど丸暗記（過学習）しにくくなるという副次効果さえあります。

不安なら、NNC で両方学習させて評価タブで比べてください。数分で答えが出ます — GUI で学習できることの、これが最大の御利益です。

## 8.3 学習結果から .nnb を直接エクスポートする

### マウス3クリックの引っ越し手続き

モデルが決まったら、Pico へ引っ越しです。手続きは NNC の画面で完結します。

1. 学習タブ（または評価タブ）の左側、**学習結果リスト**で対象の結果を**右クリック**
2. メニューの**「エクスポート」**にマウスを合わせる
3. **「NNB (NNabla C Runtime file format)」**を選ぶ

<!-- 図版: book/figures/nnc/09_nnc_export_nnb.png (エクスポートメニュー) -->

これだけです。出力された `model.nnb` は学習結果のフォルダに保存されます（場所がわからなければ、同じ右クリックメニューの「学習結果のフォルダを開く」が確実です）。

エクスポートメニューには ONNX や tflite (TensorFlow lite) といった他の形式も並んでいます。NNC で学習したモデルは他の推論エンジンにも旅立てる、という懐の深さの現れですが、本書の行き先は DNNRT なので NNB 一択です。なお、この一覧が表示されるのは **nnabla エンジンのプロジェクト**です — 第6章の「新規プロジェクトは (nnabla) で」という約束は、ここで効いていたのです。

あとは model.nnb を Pico のファイルシステムへコピーするだけ。Thonny のファイルペインで「デバイスにアップロード」するか、コマンド派は：

```sh
mpremote cp model.nnb :model.nnb
```

ファームウェアの書き換えは**不要**です。モデルはただのファイルなので、学習し直すたびに、このコピー1回で差し替えられます（第9章でこの仕組みを詳しく見ます）。

### コラム：大きなモデルで MemoryError が出たら

筆者が LeNet（310KB）を初めて Pico に載せたとき、ヒープは 451KB 空いているのに `MemoryError: allocating 316936 bytes` で落ちました。犯人はモデルの読み込みコードです。

```python
data = bytearray(f.read())   # ダメな例: read() の結果とbytearrayで一時的に2倍必要
```

`f.read()` が 317KB の塊を作り、それを `bytearray()` へコピーする瞬間、合計 634KB が必要になっていたのです。正解は、先に器を確保してから流し込むこと：

```python
buf = bytearray(os.stat(path)[6])     # ファイルサイズ分を1回だけ確保
with open(path, "rb") as f:
    f.readinto(buf)                    # 器に直接読み込む
```

サポートリポジトリの `dnnrt_loader.py` は修正済みですが、**「マイコンでは『一時的に2倍』が命取り」**という教訓は、画像バッファなどあらゆる場面で使えます。メモリの少ない世界では、データの「運び方」まで設計のうちです。

## 8.4 「速度より小ささ」— 間欠動作前提のモデル設計方針

章の締めくくりに、本書の設計哲学を数字で確認しておきます。

LeNet の 299ms と本書モデルの 90ms — 3倍以上の速度差ですが、10分に1回しか推論しないカメラにとって、**この差は完全にどうでもいい**ものです（第3章の電池の算数を思い出してください。推論時間が3倍でも、平均消費電流への影響は 0.1mA 未満です）。

一方、ヒープ残 69KB と 369KB の差は**決定的**です。メモリの余白は：

- カメラ・Wi-Fi・自分のコードの「同居スペース」であり
- 収集ツールや通知機能を後から足せる「拡張の余地」であり
- 断片化や一時確保に耐える「安定性のクッション」でもあります

だから本書の方針は一貫して「**速度より小ささ、性能より余白**」。モデルは小さく始めて、精度が本当に足りないときだけ少しずつ大きくする。この順番なら、いつでも安全側に戻れます。
