# 第1章 エッジAIの世界へようこそ — 電池で動く、考えるカメラ

## 1.1 本書で作るもの：玄関先で2週間動き続けるAIカメラ

### 完成したときの風景

まず、本書を最後まで進めたときに手に入るものをお見せします。

玄関の靴箱の上に、名刺サイズの小さな装置が置かれています。ブレッドボードに載っているのは、Raspberry Pi Pico 2 W というマイコンボードと、OV7670 という親指ほどのカメラモジュール。電源は単3電池2本。PC にも AC アダプタにも、どこにもつながっていません。

装置は、ほとんどの時間、眠っています。10分に一度だけ目を覚まし、カチッと1枚だけ写真を撮り、「玄関先に荷物があるか、ないか」を自分の頭で考えます。そして荷物を見つけたときだけ、Wi-Fi をオンにしてあなたのスマホへ通知を飛ばし、また眠りに落ちます。

```text
[14:32] 📦 置き配を検知しました
```

外出先でこの通知を受け取ったあなたは、帰り道で荷物の心配をする必要がありません。通知が来ていなければ、まだ届いていないということです。

ここで大事なことがひとつあります。**この装置は、写真をどこにも送っていません。** 玄関先の画像がクラウドにアップロードされることは一度もなく、送られるのは「あった/なかった」という判定結果だけ。画像を解釈する知能— AI が、電池で動く数百円のマイコンの中に住んでいるからです。

これが「エッジAI」です。そして本書のゴールは、このカメラを部品の購入からゼロから作り上げ、**電池だけで2週間動かす**ことです（この「2週間」は願望ではなく、筆者が実測した消費電流からの試算です。根拠は第10章でデータごとお見せします）。

### 通知1件の裏で起きていること

「荷物を検知して通知する」の裏側では、次のようなサイクルが回っています。本書の構成はこのサイクルの要素にそのまま対応しているので、ここで一度流れを追っておきましょう。今は用語がわからなくても大丈夫です。それぞれ後の章でゼロから作ります。

```text
        ┌──────────────────────────────────────────────┐
        │              1サイクル（約10分）                 │
        │                                              │
 起動 ──→ 撮影 ────→ 前処理 ───→ 推論 ───→ 判定 ─┬─→ 通知 ──→ 深い眠り
        │ 0.5秒      0.02秒     0.09秒          │   数秒      (deepsleep)
        │ カメラで    160x120を   AIモデルが      │   Wi-Fiで      6mA
        │ 1枚撮る    28x28に縮小  「ある/ない」    │   スマホへ   ↑ここで電池
        │ (第4章)    (第9章)     を判断(第9章)    │  (第10章)     寿命が決まる
        │                                       │              (第10章)
        │                              変化なしなら通知せずそのまま眠る
        └──────────────────────────────────────────────┘
```

数字に注目してください。撮影から判定までは **1秒足らず**。一方、眠っている時間は10分近くあります。つまりこの装置の電池寿命は、活動している一瞬ではなく、**いかに深く静かに眠れるか**でほぼ決まります。AI カメラの本でありながら第10章「省電力・間欠動作設計」を本書のハイライトに据えているのは、そのためです。

もうひとつ注目してほしいのは「推論 0.09秒」です。AI の推論と聞くと GPU サーバーを想像するかもしれませんが、適切に小さく設計したモデルなら、電池駆動のマイコンでも 90 ミリ秒で答えが出ます（第9章で実測します）。「マイコンで AI」は、もう背伸びした実験ではなく、実用的な設計選択肢なのです。

### 本書でやること・やらないこと

範囲を先に明確にしておきます。

**やること：**

- OV7670 カメラモジュールの配線と、PIO+DMA による画像取り込み（すべて MicroPython から制御します）
- Sony Neural Network Console（NNC）の GUI を使った、ドラッグ&ドロップでのモデル設計と学習
- 自分の設置環境で撮ったオリジナルデータセットの作成
- 学習済みモデルを Pico 2 W 上で動かす — DNNRT（Sony の推論ランタイム）の MicroPython 版を使います
- 電池駆動のための省電力設計と、消費電流の実測にもとづく電池寿命の見積もり
- Wi-Fi 経由でのスマホ通知と、応用3プロジェクト（置き配検知・長期観察カメラ・ソーラー運用）

**やらないこと（または発展として紹介にとどめること）：**

- **C 言語でのプログラミング。** 読者が書くコードは PC 側も Pico 側も 100% Python です。C で書かれた高速な推論エンジンは使いますが、それはビルド済みファームウェアとして配布するので、書き込むだけで使えます
- 動画のリアルタイム連続推論（本書は「間欠動作の静止画カメラ」に的を絞ります。この割り切りが電池駆動を可能にします）
- 物体検出（画像のどこに何があるか）。本書は画像分類（この画像は何か）までを扱い、検出は第12章で方向性のみ紹介します
- ニューラルネットワークの数学的な厳密さ。数式は最小限にし、直感と実験で理解します

### なぜこの題材なのか

「マイコンで AI」を体験するだけなら、もっと簡単な近道もあります。たとえば PC で撮った画像をマイコンに送り込めば、カメラの章はまるごと不要です。既製の AI カメラモジュールを買えば、配線も学習も省略できます。

それでも本書があえて「カメラ配線から電池運用まで」を通しでやるのは、この構成が**エッジAI開発の全工程の縮図**になっているからです。データ収集、モデル設計、学習、軽量化、デバイスへの展開、電力設計 — 実務のエッジAI プロジェクトに登場する工程が、机の上に載る規模とホビー予算で一通り体験できます。しかも「自分の玄関先」という、世界のどのデータセットにも入っていない環境で動かすからこそ、**AI は与えられたモデルを動かすものではなく、自分のデータで育てるもの**だという感覚が身につきます。

そして完成品は、実際に役に立ちます。筆者はこれが趣味の電子工作の一番の贅沢だと思っています。

次の 1.2 節では、この装置を支える「エッジAI」という考え方を、クラウドAIとの対比で整理します。

## 1.2 エッジAIとは何か — クラウドAIとの違い

### AI はどこで考えるのか

ChatGPT に質問するとき、考えているのはあなたのスマホではありません。質問文はインターネットを渡ってデータセンターに届き、巨大な GPU クラスタが推論した結果が返ってきます。これが**クラウドAI** — AI の頭脳がネットワークの向こう側にある形です。

対して**エッジAI**は、頭脳をデータの発生源のすぐそば（ネットワークの「端」= エッジ）に置きます。スマホの顔認証、イヤホンのノイズキャンセル、車の衝突防止 — これらは全部、クラウドに問い合わせず手元のチップで推論しています。

エッジにも階層があります。

```text
      クラウド          スマホ・PC           マイコン
   ┌────────────┐   ┌────────────┐   ┌────────────┐
   │ GPUクラスタ   │   │ 専用AIチップ  │   │ RP2350     │
   │ メモリ:TB級  │   │ メモリ:GB級  │   │ メモリ:520KB │
   │ 電力:kW級    │   │ 電力:W級     │   │ 電力:mW級    │
   └────────────┘   └────────────┘   └────────────┘
    何でもできる       大抵できる      できることを選ぶ
                                      ↑ 本書はここ
```

本書が挑むのは一番右、マイコンの世界です。この領域は **TinyML**（タイニー・エムエル）とも呼ばれ、ここ数年で急速に発展してきました。メモリはクラウドの100万分の1。その代わり、電力もクラウドの100万分の1。この極端な制約の中で「できることを選ぶ」のが、マイコンAIの設計思想です。

### 制約は敵ではなく設計指針

520KB のメモリと聞くと、何もできない気がするかもしれません。しかし本書の置き配検知カメラを思い出してください。必要なのは「玄関先の定点画像に荷物があるか、ないか」の2択の判断だけです。1000クラスの物体認識は要りません。毎秒30フレームの処理も要りません。

問題を絞り込めば、モデルは驚くほど小さくできます。本書で作るモデルは**わずか14KB** — フロッピーディスク1枚に100個入るサイズです。それでも、自分の玄関先というただひとつの環境に限れば、実用になる精度が出ます。

**汎用性を捨てて、特定の仕事に特化する。** これがエッジAIとクラウドAIの一番深い違いです。クラウドAIが「何でも知っている巨大な脳」なら、エッジAIは「ひとつの仕事を反射的にこなす小さな神経」です。そして家の中の困りごとの多くは、後者で十分解決できます。

## 1.3 なぜエッジで推論するのか：「画像を送らず、結果だけ送る」

### 38,400バイト対8バイト

「クラウドに画像を送って、クラウドで判定すればいいのでは?」— 当然の疑問です。実際、ネットワークカメラの多くはそうしています。ではなぜ、わざわざマイコンの中で推論するのか。数字で比べてみましょう。

本書のカメラが撮る画像は、160×120ピクセルで **38,400バイト**。一方、推論結果（「荷物あり/なし」2クラスそれぞれの確率）は **わずか8バイト**。その差は4,800倍です。

```text
   クラウド推論方式:                エッジ推論方式(本書):
   ┌──────┐  38,400バイト          ┌──────┐    8バイト
   │ Pico │ ────────────→ クラウド  │ Pico │ ──────────→ スマホ
   │      │   画像を毎回送る         │ +AI  │  結果だけ送る
   └──────┘   Wi-Fiが長時間ON      └──────┘  Wi-Fiは一瞬でOK
```

この数千倍の差が、4つの利点に化けます。

**① 省電力。** Wi-Fi 送信は本書の装置で最も電気を食う動作です（筆者の実測で約42mA — 推論中の1.4倍、深い眠りの7倍）。送るデータが小さいほど Wi-Fi をオンにする時間が短くなり、電池が長持ちします。さらに言えば、「荷物なし」が続く限り**送信ゼロ**で済みます。変化があったときだけ通知する — 判断する頭が手元にあるからこそできる節約です。

**② 通信量と通信環境。** 10分ごとに画像を送り続けると1日5MB以上。エッジ推論なら実質ゼロです。これは通信量の節約だけでなく、「Wi-Fi が弱い場所・モバイル回線・LoRa のような極細回線でも運用できる」ことを意味します。

**③ プライバシー。** 玄関先の画像は、宅配業者も、家族も、ときには通行人も写り込みます。それを外部サーバーに送り続けるのと、判定結果の1行だけ送るのとでは、安心感がまるで違います。画像はデバイスの外に一切出ない — これは説明しやすく、家族の理解も得やすい設計です。

**④ 自立性。** クラウド方式は、サーバーの障害・API の仕様変更・サービス終了で突然動かなくなります。エッジ方式のこのカメラは、玄関と Wi-Fi ルーターさえあれば動き続けます。10年後も動くかどうかを自分で決められるのは、自作の大きな価値です。

### トレードオフも正直に

いいことずくめではありません。エッジ推論には代償があります。

- **精度の上限。** 14KB のモデルは、クラウドの巨大モデルには絶対に勝てません。だからこそ「自分の環境に特化させる」戦略（第7章）が重要になります
- **更新の手間。** モデルを賢くしたいときは、デバイスに新しいモデルを配る必要があります。本書ではファイル1個のコピーで済む仕組みにします（第9章）
- **デバッグの難しさ。** 「なぜ誤判定したのか」を調べるには工夫が要ります。本書では判定に使った画像を保存しておく仕掛けを用意します（第11章）

本書はこれらの代償を隠さず、ひとつずつ対策していきます。

## 1.4 ワークフロー全体像：GUIで学習、Pythonで推論、Cは書かない

### 3つのステージ

本書の開発は、大きく3つのステージを行き来します。

```text
  ステージ1: 学習(PC)          ステージ2: 書き出し(PC)    ステージ3: 推論(Pico 2 W)
 ┌─────────────────────┐   ┌─────────────────┐   ┌──────────────────────┐
 │ Neural Network       │   │ NNC のエクスポート │   │ MicroPython + DNNRT  │
 │ Console (GUI)        │   │ 機能             │   │                      │
 │                      │   │                  │   │  import dnnrt        │
 │ ドラッグ&ドロップで     │──→│ 学習結果から      │──→│  model.forward()     │
 │ ネットワークを組み、     │   │ model.nnb を出力  │   │                      │
 │ ボタンひとつで学習      │   │ → Picoへコピー    │   │ 撮影→前処理→推論→通知  │
 │                      │   │                  │   │ →deepsleep のループ   │
 └─────────────────────┘   └─────────────────┘   └──────────────────────┘
      Pythonすら書かない       マウス操作だけ          すべてMicroPython
```

**ステージ1は Sony の Neural Network Console（NNC）。** ニューラルネットワークを、レイヤーのブロックをドラッグ&ドロップでつなぐだけで設計できる GUI ツールです。学習の進み具合も精度もグラフで見えるので、「AI の学習」という一番とっつきにくい工程が、一番視覚的な工程に変わります。プログラミングは一切登場しません。

**ステージ2は書き出し。** 学習結果を、マイコン用の軽量形式（.nnb）としてエクスポートします。これも NNC の画面操作だけで完結します（第8章）。

**ステージ3が本書の主役、Pico 2 W。** 書き出した model.nnb をファイルとしてコピーし、MicroPython から `import dnnrt` で読み込んで推論します。カメラの制御も、画像の前処理も、Wi-Fi 通知も、スリープ制御も、すべて MicroPython で書きます。

### DNNRT — SPRESENSE 育ちの推論エンジンを Pico で

ステージ3に登場した **DNNRT** について補足します。DNNRT は Sony が開発した組み込み向けの推論ランタイムで、もともと同社のマイコンボード SPRESENSE 向けに提供されているものです。NNC で学習したモデルをそのまま実行できるのが最大の特長で、面倒な形式変換や精度劣化の心配がありません。

本書では、この DNNRT を Pico 2 W (RP2350) に移植し、MicroPython のモジュールとして組み込んだファームウェアを使います。中身は C 言語で書かれた高速なエンジンですが、読者から見えるのは次のような Python の顔だけです。

```python
import dnnrt

model = dnnrt.Model(open("model.nnb", "rb").read())
model.set_input(0, pixels)   # 前処理済みの画像を渡す
model.forward()              # 推論実行 — 実測90ミリ秒
result = model.get_output(0) # 各クラスの確率が返る
```

「C の速度を、Python の書きやすさで使う」。これが本書の技術構成の核です。ファームウェアはビルド済みのものを配布するので、C コンパイラのインストールすら不要です（自分でビルドしたい人のために、手順は付録Fに用意しました）。

### なぜ MicroPython なのか

マイコン開発の定番は C/C++ です。速度もメモリ効率も C が上です。それでも本書が MicroPython を選ぶ理由は3つあります。

第一に、**このカメラには C の速度が要らない**からです。10分に1回、1秒動くだけの装置に、マイクロ秒単位の最適化は無意味です。実測でも、画像の前処理（純 Python）は19ミリ秒で終わります。

第二に、**試行錯誤の速さ**です。MicroPython は書き込み不要で、コードを送るだけで即実行できます。「閾値をちょっと変えて再実験」が5秒で回る環境は、AI の調整作業と相性抜群です。

第三に、**学習コストがひとつで済む**からです。PC 側のツールも Pico 側の制御も同じ Python 系なら、覚えることが半分になります。

「でも、カメラの画像取り込みみたいな高速処理は Python では無理では?」— 鋭い指摘です。その通りで、ピクセルを1個ずつ Python のループで拾ったら間に合いません。そこで登場するのが RP2350 の秘密兵器 **PIO**（プログラマブルI/O）と **DMA** です。詳しくは第3章と第4章で扱いますが、一言でいえば「CPU の外にある小さな専用ハードウェアに肉体労働を任せ、Python は指示だけ出す」仕組みです。Python の書きやすさとハードウェアの速度は、両立できます。

### 開発用 PC の要件

ロボットや生成 AI の本と違い、本書の PC 要件はささやかです。
