# 第4章 OV7670 カメラをつなぐ — Pico に「目」を与える

いよいよ本書最初の山場です。この章が終わると、あなたの Pico はカメラで世界を撮影し、その画像を PC の画面に映せるようになります。ジャンパワイヤ18本、レジスタ設定、PIO プログラム — 登場人物は多めですが、次の4段の階段を一段ずつ登れば、迷子にはなりません。

```text
  4段目: PC で画像が見える(4.6)          ← ゴール。感動ポイント
  3段目: 1フレームがメモリに入る(4.3〜4.5) ← PIO+DMA の出番
  2段目: 同期信号が来ていると確認できる(4.3)
  1段目: カメラと会話できる(4.2)          ← まずここ。ID が読めれば配線の大半は正しい
```

急がば回れ。**一気に4段目を目指さず、1段ずつ動作確認する**のがこの章の攻略法です。実は筆者もこの章の内容を最初に組んだとき、2つの罠にはまりました。その顛末も包み隠さず書きます — 同じ穴に、あなたがはまらないように。

## 4.1 OV7670 の仕組みと配線図

### 600円のカメラの正体

OV7670 は、OmniVision 社の30万画素イメージセンサーです。設計は古く、もともとは2000年代の携帯電話向け。だからこそ枯れていて、資料が豊富で、そして安い（約600円）。低解像度・低速で構わない本書の用途には、むしろ理想的な選択です。

購入時の注意は第1章でも触れた **「FIFO なし版」を選ぶ**こと。世の中には画像バッファ（FIFO）チップ付きの高い版もありますが、本書では Pico の PIO+DMA がその役割を果たすので不要です。見分け方：モジュール裏面に大きめの IC（AL422B）が載っていたら FIFO あり版です。何も載っていないシンプルな基板が、本書の相棒です。

### カメラは「自分では何もしない」

OV7670 の動作を理解する鍵は、**このカメラが完全な受け身である**ことです。電源をつないでも、何も起きません。クロック（XCLK）を外から供給されて初めて心臓が動き出し、設定（SCCB）を書き込まれて初めて撮り方が決まり、そして動き出したら**こちらの都合はお構いなしに**画素データを一方的に送り続けます。

信号線の役割を整理します。

| グループ | 信号 | 向き | 役割 |
|---|---|---|---|
| 電源 | 3.3V / GND | → | 電源。本書は 3.3V 直結 |
| 設定 | SIOD / SIOC | ⇄ | SCCB（I2C 互換）。レジスタの読み書き |
| 心臓 | XCLK | → | 動作クロックの供給。**これがないと何も始まらない** |
| 同期 | VSYNC | ← | 「新しいフレームが始まるよ」の合図 |
| 同期 | HREF | ← | 「いまの1行は有効データだよ」の合図 |
| 同期 | PCLK | ← | 「いまデータが確定したよ」の合図（画素クロック） |
| データ | D0〜D7 | ← | 画素データ本体（8bit パラレル） |
| 管理 | RESET / PWDN | → | リセットと省電力停止（第10章で活躍） |

矢印に注目してください。こちらから与えるのは電源・設定・クロックだけ。あとはカメラが吐き出す信号を、こちらが**必死に受け止める**構図です。その「必死に」を担当するのが前章で学んだ PIO でした。

### 配線表 — 18本の橋を架ける

本書標準のピン割り当てです。第5章以降のコードもすべてこの配線を前提にします。

| OV7670 | Pico 2 W | 備考 |
|---|---|---|
| 3.3V | 3V3(OUT)（36番ピン） | |
| GND | GND（38番ピンなど） | |
| SIOD | GP0 | SCCB データ |
| SIOC | GP1 | SCCB クロック |
| D0〜D7 | **GP2〜GP9** | **順番厳守・連続8本**（理由は 4.3 で） |
| PCLK | GP10 | |
| HREF | GP11 | |
| VSYNC | GP12 | |
| XCLK | GP13 | **配線を最短に**（クロックはノイズに敏感） |
| RESET | 3.3V | プルアップ済みモジュールは未接続でも可 |
| PWDN | GND | プルダウン済みモジュールは未接続でも可 |

配線のコツを3つ。**（1）D0〜D7 の順番を指差し確認する。** この8本の並び間違いが、この章のトラブルの王様です。**（2）XCLK（GP13）は最短経路で。** 15MHz のクロックが通る線なので、長いワイヤはノイズ源になります。**（3）色分けする。** 電源系は赤黒、データ系は同系色でそろえる — 未来の自分への親切です。

## 4.2 SCCB 設定は machine.I2C、XCLK 供給は machine.PWM で

### まず心臓を動かす — PWM で 15MHz を作る

階段の1段目は「カメラと会話できること」。そのためにはまず XCLK の供給です。専用のクロック IC は使いません。Pico の **PWM（パルス幅変調）を周波数 15MHz・デューティ比 50% で回せば、それは立派なクロック**です。

```python
from machine import Pin, PWM
xclk = PWM(Pin(13), freq=15_000_000, duty_u16=32768)  # 32768/65535 ≒ 50%
```

たった1行。RP2350 のシステムクロック 150MHz をちょうど10分周できるので、15MHz はきれいに作れます。

### SCCB は「方言のある I2C」

カメラの設定インターフェース SCCB は、I2C とほぼ同じ電気仕様です。MicroPython の `machine.I2C` がそのまま使えます。

```python
from machine import I2C
i2c = I2C(0, sda=Pin(0), scl=Pin(1), freq=100_000)
i2c.scan()   # → [33]  (0x21 = OV7670 のアドレス)
```

ただし方言がひとつ。I2C の標準的なレジスタ読み出しは「書き込みと読み出しを一息で行う（リピーテッドスタート）」のですが、**SCCB はこれに対応していません**。読み出しは「読みたいレジスタ番号を書く」「改めて1バイト読む」の2段に分ける必要があります。

```python
OV7670_ADDR = 0x21

def sccb_read(reg):
    i2c.writeto(OV7670_ADDR, bytes([reg]))      # 1段目: 番号を伝える
    return i2c.readfrom(OV7670_ADDR, 1)[0]      # 2段目: 改めて読む

def sccb_write(reg, val):
    i2c.writeto(OV7670_ADDR, bytes([reg, val]))
```

`readfrom_mem()` のような便利メソッドを使うと（内部でリピーテッドスタートを使うため）失敗します。地味ですが、OV7670 攻略の関所のひとつです。

### 1段目クリアの儀式 — ID を読む

OV7670 は、レジスタ 0x0A と 0x0B に自分の ID を焼き込んで出荷されています。読んでみましょう。

```python
>>> hex(sccb_read(0x0A)), hex(sccb_read(0x0B))
('0x76', '0x73')
```

**0x76 と 0x73 が返ったら、1段目クリアです。** 電源・SCCB 2本・XCLK の配線が正しいことが、この2バイトで一挙に証明されました（XCLK が届いていないとカメラは SCCB にすら応答しないので、実は XCLK の確認も兼ねているのです）。エラーが出る場合は SIOD/SIOC の入れ替わりと XCLK 配線を疑ってください。

### 撮り方をダイヤルで合わせる — レジスタ設定

OV7670 には約200個のレジスタ（設定ダイヤル）があり、解像度・色形式・クロック分周などをここで決めます。本書の設定方針は：

- **解像度は QQVGA（160×120）**。AI の入力（28×28）には十分すぎるほどで、メモリにやさしい
- **色形式は RGB565**。1画素を2バイト（赤5bit＋緑6bit＋青5bit）で表す形式です

```text
   RGB565 の 1画素 = 2バイト:
   ┌─────────────────┬─────────────────┐
   │ 1バイト目          │ 2バイト目          │
   │ R R R R R G G G  │ G G G B B B B B  │
   └─────────────────┴─────────────────┘
     赤5bit    緑の上3bit   緑の下3bit  青5bit
```

設定するレジスタは全部で20個弱。全リストは付録 B に譲り、ここでは物語の鍵を握る3つだけ紹介します。

- **COM7（0x12）に 0x80 を書くとソフトリセット。** 設定はまっさらに戻ります。何かおかしくなったら、ここからやり直せます
- **COM15（0x40）= 0xD0 で RGB565 を選択**
- **COM10（0x15）= 0x20 で「行の隙間では PCLK を止める」設定に。** これが次節の PIO プログラムを助けます

サポートリポジトリの `ov7670.py` に、リセットから全設定までを行う `init_qqvga_rgb565()` を用意してあります。以降はこれを使って進めます。

## 4.3 `@rp2.asm_pio` で書くピクセル取り込み — HREF 行頭再同期方式

### 2段目 — 信号は来ているか

設定を書き込んだカメラは、もう画像を送り始めています。PIO を書く前に、まず「信号が来ていること」を目で確かめましょう（階段2段目）。VSYNC のエッジ（変化）を数える素朴なコードで十分です。

```python
import time
vsync = Pin(12, Pin.IN)

def count_edges(pin, ms=300):
    n, last = 0, pin.value()
    t0 = time.ticks_ms()
    while time.ticks_diff(time.ticks_ms(), t0) < ms:
        v = pin.value()
        if v != last:
            n += 1
            last = v
    return n

>>> count_edges(vsync)
2        # 0でなければフレームが流れている証拠
```

### 【罠その1】RP2350 では Pin を「入力」で初期化しないと PIO から見えない

さて、ここで筆者がはまった1つ目の罠です。最初に組んだとき、PIO プログラムは完璧なはずなのに、取り込みが永遠に終わりませんでした。原因は上のコードの `Pin(12, Pin.IN)` — 正確には、**それを一部のピンでやっていなかった**ことです。

RP2350 では、`Pin(n, Pin.IN)` で入力として初期化していないピンは、入力回路が有効化されず、**PIO からも信号が見えません**。PIO は存在しない信号の変化を待ち続け、プログラムは静かに固まります。エラーは一切出ません。

対策は単純で、**PIO が参照する全ピンを事前に `Pin(n, Pin.IN)` しておく**こと。D0〜D7、PCLK、HREF、VSYNC の11本です。サポートリポジトリのドライバは初期化時にこれを済ませていますが、自分で書く人は必ず思い出してください。「PIO が無言で固まったら、まず Pin.IN を疑う」— 覚える価値のある教訓です。

### 【罠その2】素朴な取り込みは「縞と斜め」になる

2つ目の罠は、もっと示唆に富んでいます。最初に書いた PIO プログラムは、こんな素朴な発想でした。

> COM10 の設定で「データがあるときだけ PCLK が動く」ようにしたのだから、PCLK が立ち上がるたびに 8bit 拾えばいいはずだ

6命令で書けるエレガントな方法に見えました。ところが撮れた画像は — **1行ごとにマゼンタと緑の縞が走り、全体が斜めに歪んだ、悪夢のような絵**だったのです。

<!-- 図版TODO: 罠その2の症状画像。旧版PIOプログラム(v1_test_report.md 参照)で再現撮影する -->

原因を分析すると、こうでした。1行は 160画素 × 2バイト = **320バイト**のはずが、行の境目で余分な PCLK エッジを拾い、ときどき 321 バイトになっていた。すると次の行は 1 バイトずれて始まります。RGB565 は2バイトで1画素ですから、**1バイトのずれは「色の読み枠」の半画素ずれ** — これが行ごとの色縞の正体。そして毎行すこしずつ横に流れる — これが斜めの正体です。

教訓：**信号は仕様書どおりには来ない。ずれても自動復帰する設計にせよ。**

### 改良版 — 行の頭で毎回「仕切り直す」

対策は、行の始まり（HREF の立ち上がり）で毎回同期を取り直し、**1行きっかり320バイトを数えて取り込む**ことです。数え終えたら次の HREF まで何も拾わない。これなら境目に何が来ようと、次の行は必ず正しい位置から始まります。完成した PIO プログラムが以下、全11命令です。

```python
@rp2.asm_pio(
    in_shiftdir=rp2.PIO.SHIFT_RIGHT,  # 取り込んだバイトを右詰めで積む
    autopush=True, push_thresh=32,    # 32bit(4バイト)たまるごとに自動でFIFOへ
)
def capture():
    pull()                  # ① 「1行のバイト数-1」をCPUから受け取る
    mov(y, osr)             # ②   それをYレジスタに保管(=319)
    wait(1, gpio, 12)       # ③ VSYNCが立つのを待ち…
    wait(0, gpio, 12)       # ④   下がった瞬間 = フレームの先頭
    wrap_target()           # ---- ここから1行ぶんのループ ----
    mov(x, y)               # ⑤ 行内カウンタXに319を再セット
    wait(0, gpio, 11)       # ⑥ 前の行のHREFが終わるのを確認し…
    wait(1, gpio, 11)       # ⑦   立ち上がった瞬間 = 行の先頭(毎行仕切り直し!)
    label("pix")
    wait(0, gpio, 10)       # ⑧ PCLKが下がって…
    wait(1, gpio, 10)       # ⑨   上がった瞬間 = データ確定
    in_(pins, 8)            # ⑩ D0〜D7の8bitを取り込む
    jmp(x_dec, "pix")       # ⑪ Xを減らしながら320回繰り返す → 次の行へ
    wrap()
```

ポイントを3つ補足します。

**「1行のバイト数」は外から渡す（①②）。** 320 という数字をプログラムに焼き込まず、実行時に CPU から受け取ります。PIO の世界では、32 以上の数値を命令に直接書けないための工夫ですが、おかげで解像度を変えても手順書はそのまま使えます。

**`in_(pins, 8)` が8本まとめ読みできる理由（⑩）。** PIO の入力命令は「基準ピンから連続した n 本」を一気に読みます。配線表で D0〜D7 を **GP2〜GP9 の連続8本・順番厳守**としたのは、この命令のためだったのです。

**32命令制限には余裕（11/32）。** 前章で予告した制約の中に、しっかり収まりました。

## 4.4 `rp2.DMA` でフレームバッファへ転送する

### 検品係の隣にベルトコンベアを置く

PIO は拾ったデータを FIFO という小さなかご（数バイト分）に入れるだけです。かごが溢れる前に、誰かがメモリへ運ばなければなりません。CPU が運ぶと本末転倒なので、ここで運搬係 **DMA** の出番です。

```python
import rp2
from machine import mem32

buf = bytearray(160 * 120 * 2)          # 38,400バイトのフレームバッファ

dma = rp2.DMA()
ctrl = dma.pack_ctrl(
    size=2,           # 4バイト(32bit)単位で運ぶ
    inc_read=False,   # 読み元(PIOのFIFO)は固定番地
    inc_write=True,   # 書き先(バッファ)は1つずつ進める
    treq_sel=4,       # 「PIO 0 のかごにデータが来たら運ぶ」という同期指定
)
dma.config(read=0x50200020,             # PIO 0 の受信FIFOの番地
           write=buf,
           count=len(buf) // 4,         # 38,400バイト ÷ 4 = 9,600回
           ctrl=ctrl, trigger=True)
```

`0x50200020` という生の番地が出てきて面食らうかもしれませんが、これは「PIO 0 号機の受信かごの住所」で、RP2350 のデータシートに載っている固定値です。DMA は住所しか理解しない実直な運搬係なのです。

もうひとつ、4.3 のプログラム冒頭にあった `SHIFT_RIGHT` + 32bit 自動プッシュの意味がここで効いてきます。バイトを右詰めで4つ積んでから運ぶと、**メモリ上に「届いた順」どおりに並ぶ**のです（RP2350 がリトルエンディアンであることとの合わせ技です。深入りは不要ですが、「順番が保証されるようにできている」と安心してください）。

### 撮影の一部始終

部品がそろいました。1フレーム撮る手順は：

```text
 ① PIOを停止し、プログラム先頭へ巻き戻す(restart)
 ② 前回の食べ残しがあればFIFOを空にする
 ③ 「1行 = 320バイト」をPIOに渡す(put(319))
 ④ DMAに「9,600回運んだら終わり」をセットして待機させる
 ⑤ PIOに号令(active(1)) → VSYNCを待って取り込み開始
 ⑥ CPUはDMAの「運び終わりました」を待つだけ
```

サポートリポジトリの `ov7670.py` では、この一連を `cam.capture(buf)` の1呼び出しに包んであります。

```python
from ov7670 import OV7670, FRAME_BYTES
cam = OV7670()                # 配線表どおりなら引数なしでOK
cam.init_qqvga_rgb565()
buf = bytearray(FRAME_BYTES)
cam.capture(buf)              # ← 3段目クリア。実測 約0.4〜0.7秒
```

戻ってくるまでの時間は筆者の実測で 427ms 前後（うち大半は次の VSYNC を待つ時間です）。エラーも例外もなく戻ってきたら、`buf` の中にはもう玄関先なり机の上なりの光景が入っています。

## 4.5 CLKRC レジスタで PCLK を落とす — 間欠動作カメラなら遅くてよい

### 速さを捨てる勇気

ところで、OV7670 は本来 30fps で動けるカメラです。それをこの章では、なぜかずいぶんゆっくり動かしています。クロックの流れを図にすると：

```text
  XCLK 15MHz ──→ [CLKRC で 1/4] ──→ 内部クロック 3.75MHz
                                       │
                                [スケーリング部で さらに 1/4]
                                       ↓
                                  PCLK ≒ 0.94MHz (1バイト/クロック)
                                       ↓
                        1フレーム 38,400バイト ≒ 41ms + 行間・フレーム間の休み
```

CLKRC（0x11）はカメラ内部の分周ダイヤルで、本書は「1/4」に設定しています。もっと速くもできるのに、あえて遅くする理由は2つあります。

**第一に、速さが要らないから。** 本書のカメラは10分に1枚撮る装置です。1フレーム 41ms も 4ms も、体感はゼロ対ゼロ。速くして得るものがありません。

**第二に、遅いほど頑丈だから。** PCLK が遅いほど、ブレッドボードのゆるい接触や長いジャンパワイヤに対する余裕（マージン）が生まれます。1MHz 弱という速度は、「手作りの配線でも安定して動く」ラインを狙った設計です。もし画像がときどき乱れるなら、CLKRC をさらに大きな分周に振る手もあります — 遅くする方向のチューニングは、いつでも安全な逃げ道です。

高性能を追わず、成立性を買う。エッジ設計らしい割り切りとして、この考え方ごと持ち帰ってください。

## 4.6 取り込んだ画像を PC に送って表示する（最初の山場・登頂）

### フラッシュに保存し、PC へ回収する

`buf` の中身を人間の目で確かめましょう。まず Pico のフラッシュにファイルとして保存します。

```python
with open("frame.raw", "wb") as f:
    f.write(buf)
```

PC への回収は Thonny が簡単です。表示メニューから「ファイル」ペインを開くと、上下2段（PC 側と MicroPython デバイス側）のファイル一覧が出ます。デバイス側の `frame.raw` を右クリック →「〜をダウンロード」で PC に保存できます（コマンド派には `mpremote cp :frame.raw .` という道もあります）。

### RGB565 を PNG に変換して、ご対面

`frame.raw` は生のピクセル値の羅列なので、そのままでは画像ビューアで開けません。PC 側で PNG に変換する小さな Python スクリプト `convert_frame.py` をサポートリポジトリに用意しました。中身は「2バイトずつ読んで R/G/B に分解し、画像として保存する」だけの素直なコードです。

```sh
python convert_frame.py frame.raw
# → frame.png (3倍に拡大した 480×360) が生成される
```

生成された frame.png を開いてください。160×120 のざらついた小さな画像 — でも、そこに映っているのは紛れもなく、**あなたの Pico が自分の目で見た世界**です。露出もピントも完璧ではないでしょう。それでもこの1枚は、この本の中で最初の大きな達成です。おめでとうございます、登頂です。

### うまく撮れないときの診察室

症状から原因を逆引きする表を置いておきます。この章のすべての知識の凝縮です。

| 症状 | 疑うべき原因 | 処方箋 |
|---|---|---|
| `capture()` が固まる/タイムアウト | PCLK・VSYNC が PIO から見えていない | 配線確認。**全ピン `Pin(n, Pin.IN)` したか**（罠その1） |
| ID (0x76) が読めない | SCCB か XCLK の配線 | SIOD/SIOC の入れ替わり、GP13 の接触を確認 |
| 縞模様・画像が斜めに流れる | 行のバイトずれ | 本書の HREF 再同期版 PIO を使っているか（罠その2）。D0〜D7 の順番も確認 |
| 色が全体に変（青とオレンジが逆など） | 2バイトの順序解釈 | `convert_frame.py --swap` で入れ替えて変換 |
| 真っ白/真っ黒 | 露出の自動調整が未整定 | 初期化後 0.3 秒待ってから撮る。照明を変えてみる |
| ときどき乱れる | 配線の接触・ノイズ | ワイヤを短く。CLKRC の分周を増やして PCLK をさらに遅く |

### この章のチェックリスト

- [ ] ID 読み出しで 0x76 / 0x73 が返った（1段目）
- [ ] VSYNC のエッジが観測できた（2段目）
- [ ] `cam.capture(buf)` が1秒以内に戻ってくる（3段目）
- [ ] PC で frame.png が開けて、映っているものが認識できた（4段目・登頂）
