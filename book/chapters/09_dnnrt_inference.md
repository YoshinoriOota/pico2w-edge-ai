# 第9章 DNNRT で推論を動かす — 学習させた我が子をマイコンで走らせる

model.nnb を手にした今、残る工程はひとつ — Pico の上で走らせることです。この章では `import dnnrt` から始めて、カメラ画像を推論につなぎ、最後に**PC と Pico が寸分違わず同じ答えを出すこと**を数値で確かめます。第4章がハードウェアの山場だったとすれば、この章はソフトウェアの山場 — そして頂上からの眺めがいちばんいい章です。

## 9.1 `import dnnrt` — model.nnb 読み込みから推論まで

### 最小の推論プログラム

まずはカメラ抜きで、推論だけを最短距離で動かします。第8章でエクスポートした `model.nnb` を Pico にコピーしたら（`mpremote cp model.nnb :model.nnb` または Thonny でアップロード）、REPL で次を実行してください。

```python
import dnnrt
import dnnrt_loader                      # サポートリポジトリの補助モジュール

model = dnnrt_loader.load_model("model.nnb")
print(dnnrt_loader.summary(model))       # 入出力の形を確認

n = 28 * 28
model.set_input(0, [0.5] * n)            # ダミー入力(全画素グレー)
model.forward()                          # ← ここで推論が走る
print(model.get_output(0))               # クラスごとの確率
model.close()
```

`summary()` の出力はこんな具合です（第7章の2クラスモデルの例）：

```text
nnabla version : 1.24.0.dev1
runtime version: 1.2.0.dev1_c1
nnb format     : 3
input[0]  shape=(1, 1, 28, 28) dtype=float32 fp_pos=0 size=3136bytes
output[0] shape=(1, 2) dtype=float32 fp_pos=0 size=8bytes
```

API は4つ覚えれば足ります。**`set_input(0, データ)`** で入力をセットし、**`forward()`** で推論を実行、**`get_output(0)`** で確率のリストを受け取る。使い終わったら **`close()`**。裏側では Sony の nnabla-c-runtime（C 実装）が動いていますが、表側はこれだけの Python です。

`get_output(0)` が返すリストは Softmax の出力（第5章）なので、最大値の位置が判定クラス、その値が確度です。

```python
out = model.get_output(0)
best = max(range(len(out)), key=lambda i: out[i])
print("class %d (%.1f%%)" % (best, out[best] * 100))
```

クラス番号と意味の対応は、第7章の `make_nnc_dataset.py` が表示した「フォルダ名昇順」の割り当て（box=0、empty=1…）です。メモしておいたものがここで効きます。

## 9.2 ファームウェアを再ビルドせずにモデルだけ入れ替えられる仕組み

なぜ model.nnb はコピーするだけで動くのか — この分業は本書の構成の要なので、一度だけ仕組みを覗いておきます。

```text
  ファームウェア (firmware.uf2)        model.nnb (ただのファイル)
  ┌───────────────────────┐         ┌──────────────────────┐
  │ MicroPython 本体         │         │ ネットワークの構造        │
  │ dnnrt モジュール (C実装)   │ ←読む── │ (層の並びと設定)          │
  │  = 汎用の「実行エンジン」   │         │ 学習済みの重み 約3,500個   │
  └───────────────────────┘         └──────────────────────┘
       焼くのは最初の1回だけ                学習し直すたびに差し替え
```

dnnrt モジュールは「NNB 形式ならなんでも実行できる汎用エンジン」で、モデル固有の情報は一切持ちません。曲（モデル）を差し替えても、プレーヤー（ファームウェア）はそのまま — 音楽プレーヤーと同じ関係です。

この分業の恩恵は、開発のリズムに現れます。「データを撮り直す → NNC で再学習 → エクスポート → `mpremote cp` → 即テスト」。**1周のサイクルにファームウェアの再ビルドもボードの再配線も入りません。** 精度チューニングの試行錯誤（第11章で何度もやります）が、コピー1回分の手軽さで回るのです。

## 9.3 前処理の実装 — カメラの絵をモデルの入力に変える

### 160×120 カラーから 28×28 グレーへ

カメラのフレーム（160×120、RGB565、38,400バイト）と、モデルの入力（28×28、グレースケール、0.0〜1.0）の間には隙間があります。埋めるのが**前処理**です。本書の前処理は3手：

```text
  160×120 RGB565 ─①切り出し→ 中央112×112 ─②間引き→ 28×28 ─③変換→ 0.0〜1.0のリスト
                    (4の倍数で28×28に        (4画素ごとに1つ拾う)    (グレー化して÷255)
                     割り切れる範囲)
```

そして第7章の鉄則その1を思い出してください — **このロジックは、収集ツールが学習画像を作ったときと1画素単位で同一**でなければなりません。コードはサポートリポジトリ（`code/integrated/` の各スクリプトが使う `preprocess()`）にありますが、骨格はこうです：

```python
def preprocess(buf, float_out):
    """RGB565フレームの中央112x112を4画素間引きで28x28グレーに変換する."""
    k = 0
    for j in range(28):
        row = (4 + j * 4) * 160          # ①切り出し + ②間引き (Y方向)
        for i in range(28):
            idx = (row + 24 + i * 4) * 2 # ①切り出し + ②間引き (X方向)
            v = (buf[idx] << 8) | buf[idx + 1]
            r = (v >> 8) & 0xF8          # ③RGB565から8bit値を復元し
            g = (v >> 3) & 0xFC
            b = (v << 3) & 0xF8
            gray = (r + g + g + b) >> 2  #   緑を2倍重みで輝度化(人の視感度に合わせた近似)
            float_out[k] = gray / 255.0  #   ÷255 ← NNCの Image Normalization と一致!
            k += 1
```

最後の `÷255` が、第6〜7章でしつこく確認した「Image Normalization (1.0/255.0)」との待ち合わせ場所です。784画素のループは純 Python で **実測19ms** — 第1章で予告したとおり、この規模なら高速化の小細工は不要です。

### `set_input` の2つの顔

`set_input(0, データ)` には2種類の渡し方があります。

- **float のリスト**（本書の標準）：`[0.0〜1.0] × 784` を渡すと、dnnrt が内部で float32 に変換します。わかりやすさ優先
- **生バイト列**（上級）：入力テンソルとバイト単位で同じ形式（float32 の 3,136 バイト）の `bytearray` を渡すと、変換なしの丸ごとコピーになります。前処理の出力を最初から float32 の bytearray で組み立てられるなら、こちらが最速です

本書は一貫してリスト方式で書きます。速度が問題になったときの引き出しとして、生バイト列の存在だけ覚えておいてください。

## 9.4 撮影から判定まで — 一気通貫と実測

部品がそろいました。つなげます。

```python
import time
import dnnrt_loader
from ov7670 import OV7670, FRAME_BYTES

cam = OV7670()
cam.init_qqvga_rgb565()
frame = bytearray(FRAME_BYTES)
model = dnnrt_loader.load_model("model.nnb")
fvec = [0.0] * 784
CLASSES = ["box", "empty"]               # make_nnc_dataset.py の割り当て表

while True:
    cam.capture(frame)
    preprocess(frame, fvec)
    model.set_input(0, fvec)
    model.forward()
    out = model.get_output(0)
    best = max(range(len(out)), key=lambda i: out[i])
    print("%s (%.1f%%)" % (CLASSES[best], out[best] * 100))
    time.sleep(5)
```

30行足らずの「考えるカメラ」です。カメラの前に物を置いたりどけたりして、判定が切り替わるのを眺めてください — 第1章の風景まで、あと通知とスリープを残すだけです。

性能も測っておきます。`time.ticks_ms()` を挟んだ筆者の実測（14KB・2値系モデル）：

| 工程 | 実測 |
|---|---|
| 撮影（VSYNC 待ち含む） | 472〜743 ms |
| 前処理（純 Python、784画素） | 19 ms |
| **推論（forward）** | **90 ms** |
| 出力取得 | 1 ms 未満 |
| メモリ（全リソース確保後のヒープ残） | 369 KB |

意外なことに、一連の中でいちばん遅いのは AI ではなく**カメラ**です（次の VSYNC を待つ時間が支配的）。推論の 90ms は、RP2350 が約80万回どころか数万回の積和演算を C の速度でこなした結果で、間欠動作カメラには十分すぎる俊足です。

## 9.5 PC の NNC 評価結果と Pico 実機の出力を突き合わせる

### 「同じ答え」をどう証明するか

ここまでで動くものはできました。しかし、エッジAIの移植には最後の関門があります — **Pico の上で動いているこのモデルは、本当に PC で学習させたあのモデルと同じ判断をしているのか？** 前処理のずれ、形式変換の劣化、ランタイムの実装差…疑おうと思えばいくらでも疑えます。

証明の方法は簡単です。**同じ入力を両方に食わせて、出力の数値を突き合わせる。** NNC の評価タブは1枚ごとの出力値（y'_0, y'_1, …）を表示してくれるので、照合値には困りません。

### 実験 — 7桁の一致

筆者が実際にやった検証をお見せします。題材は第6章の LeNet（Fashion-MNIST）。評価タブで、検証データ先頭の画像（Ankle boot）の出力を控えます — `y'_0 = 9.9516555e-08`。次に**同じ画像**を Pico に転送し、同じ 1/255 正規化で LeNet の .nnb に入力しました。結果：

```text
  NNC 評価タブ (PC)   : y'_0 = 9.9516555e-08   判定 class 9
  Pico 実機 (dnnrt)   : y'_0 = 9.951655e-08    判定 class 9 (確度 0.999909)
```

**float32 の有効桁数（約7桁）いっぱいまで、完全に一致。** 「だいたい同じ」ではありません。学習で決まった数千個のダイヤルが、エクスポートを経ても1ビットも化けず、マイコンの上で同じ計算を再現している — その動かぬ証拠です。

### あなたのモデルでの確認手順

自分のモデルでも、納品前の儀式としてぜひやってください。

1. NNC の評価タブで、検証画像を1枚選び、y' の値を控える（行をクリックすると全クラス分見えます）
2. その画像ファイル（第7章で作った 28×28 PNG）の画素値を 1/255 して Pico の `set_input` に渡す
3. `get_output(0)` の値と控えた値を比べる — 有効桁で一致すれば合格

ここで一致しない場合、疑うべきは**ほぼ100%前処理**です（ランタイムは上の実験が示すとおり正確です）。画素の並び順、正規化の係数、画像の取り違え — 第7章の鉄則その1に立ち返って点検してください。逆に言えば、この儀式が通れば「実機で精度が出ない」ときの容疑者リストからモデルとランタイムを外せる — 切り分けの強力な武器になります。

## 9.6 DNNRT 対応レイヤーの制約 — 鉄板の部品で組む

最後に、第5章から引っ張ってきた注意点を回収します。DNNRT（nnabla-c-runtime）は nnabla の全レイヤーを実装しているわけではなく、**未対応のレイヤーを含むモデルは .nnb にできても実行時にエラー**になります。

本書で使ってきた部品 — **Input / Convolution / ReLU / MaxPooling / Affine / Softmax（+ 学習専用の CategoricalCrossEntropy と ImageAugmentation。この2つはエクスポート時に自動的に外れます）** — はすべて対応済みの「鉄板」です。この範囲で組んでいる限り、制約を意識する場面はありません。

NNC のパレットで冒険したくなったら、付録 C の対応表を確認してから使ってください。目安として、画像分類の定番部品（BatchNormalization、Dropout、Tanh、Sigmoid など）はおおむね動きます。凝った新顔（Attention 系など）は要確認です。「**編集タブで1ブロック足すたびに、付録 C をチラ見**」— これで事故は防げます。
