# 第10章 省電力・間欠動作設計 — 電源ケーブルを切り落とす（本書のハイライト）

考えるカメラは完成しました。しかし第9章の最後の姿は、USB ケーブルにつながれた据え置き機です。この章で、いよいよ電池だけで動く自立した装置に仕立てます。

これまで何度も予告してきたとおり、この装置の電池寿命は「派手な推論」ではなく「**眠りの深さ**」で決まります。そしてスリープの世界は、データシートの字面と実測が食い違う魔境でもあります。この章は本書でいちばん実測データが多い章です — 筆者が電流計とにらめっこして取った数字を、罠も含めてすべてお見せします。

## 10.1 間欠動作の設計パターン — main.py に「一生」を書く

### 設計の全体像

第1章の風景をコードの構造に翻訳すると、こうなります。

```text
        電源ON (または deepsleep からの復帰 = リセット)
          │
          ▼
   ┌─ main.py 実行開始 ──────────────────────────────┐
   │  ① 脱出ハッチ (数秒待つ — 開発者がCtrl+Cできる窓)   │
   │  ② カメラ初期化 → 撮影 → 前処理 → 推論             │
   │  ③ 判定が「変化」していたら:                        │
   │       Wi-Fi ON → 通知送信 → Wi-Fi OFF             │
   │  ④ カメラを眠らせる                                │
   │  ⑤ machine.deepsleep(10分)                       │
   └──────────────────────── ⑤の復帰は①へ戻る ────────┘
```

鍵は、**rp2 ポートの `machine.deepsleep()` は「復帰＝リセット」**だという性質です（筆者の実機確認による挙動です）。目覚めたとき、プログラムは眠った場所の続きからではなく、**main.py の先頭から**再スタートします。変数もメモリも毎回まっさら。

一見不便に思えますが、第2章で学んだ「main.py は電源投入で自動実行」と組み合わせると、これは**理想の設計様式**に化けます。間欠動作カメラの1サイクルを main.py に書けば、「deepsleep → リセット → main.py → deepsleep → …」という永久ループが、OS もスケジューラもなしに完成するのです。毎回コールドスタートなので、メモリリークも状態の腐敗も原理的に起きません。10分ごとに生まれ変わる装置 — 長期運用にとって、これほど頑丈な構造はありません。

### 完成形 main.py の骨格

本書の最終形を先に見せます（完全版はサポートリポジトリ、ここは骨格です）。

```python
# main.py — 電池駆動エッジAIカメラ (本書の最終形の骨格)
import time, machine

INTERVAL_MIN = 10          # 撮影間隔
GRACE_SEC = 5              # ①脱出ハッチ: 起動後この秒数は何もしない

time.sleep(GRACE_SEC)      # ← この間に Thonny から Ctrl+C すれば開発モードへ

import dnnrt_loader
from ov7670 import OV7670, FRAME_BYTES
from notify import send_udp          # 10.5で作る通知関数
from preprocess import preprocess    # 第9章の前処理

def run_once():
    cam = OV7670()
    cam.init_qqvga_rgb565()
    frame = bytearray(FRAME_BYTES)
    model = dnnrt_loader.load_model("model.nnb")
    fvec = [0.0] * 784

    cam.capture(frame)               # ②撮影
    preprocess(frame, fvec)
    model.set_input(0, fvec)
    model.forward()                  # ②推論
    out = model.get_output(0)
    best = max(range(len(out)), key=lambda i: out[i])

    prev = read_last_state()         # 前回の判定 (フラッシュの小さなファイル)
    if best != prev:                 # ③変化があったときだけ
        send_udp("class=%d p=%.2f" % (best, out[best]))
        write_last_state(best)

    cam.deinit()                     # ④カメラを眠らせる (10.4)

run_once()
machine.deepsleep(INTERVAL_MIN * 60 * 1000)   # ⑤ 目覚めると main.py 先頭へ
```

「前回の判定」をフラッシュ上の小さなファイルに置くのがささやかな工夫です。deepsleep でメモリは消えますが、フラッシュは消えない — 「机は毎回片付くが、本棚は残る」（第3章）をここで活用します。おかげで「荷物が置かれた瞬間」と「回収された瞬間」だけ通知が飛び、置きっぱなしの10分ごとの再通知は起きません。

### コラム：main.py 地獄と脱出ハッチ

main.py 方式には有名な副作用があります。**電源を入れるたびに勝手に走り出すので、開発者がコードを直したくても割り込む隙がない**のです（すぐ deepsleep に入られると、シリアルすら応答しません）。筆者はこれで一度、収集運用中の Pico を捕まえるのに冷や汗をかきました。

対策が骨格①の**脱出ハッチ** — 起動直後の数秒の空白です。この間に Thonny を接続して Ctrl+C（または `mpremote` でアクセス）すれば main.py は中断され、いつもの REPL に戻れます。`GRACE_SEC = 5` の5秒は、電池寿命への影響が誤差の範囲なのに、開発の安心感は絶大です。**自動実行するデバイスには、必ず人間用の裏口を作っておく** — 組み込み開発の生活の知恵です。

## 10.2 `lightsleep` / `deepsleep` の実際 — 実測で何mAまで下がるか

理屈の前に、実測値をどうぞ（測定方法は10.6で詳述。USB 給電経路での値なので、電池直結ではもう少し下がります）。

| 状態 | 実測 | 対アイドル比 |
|---|---|---|
| アイドル（REPL 待機） | 17.7 mA | 1.0 |
| `machine.lightsleep()` 中 | 10.1 mA | 0.57 |
| **`machine.deepsleep()` 中** | **6.0 mA** | **0.34** |

2つのスリープの違いを整理します。

- **lightsleep(ms)**：浅い眠り。クロックを止めて待ち、**続きから**目覚めます。メモリも変数も保持。Wi-Fi 接続状態を保ったまま短時間待つ、といった用途向き
- **deepsleep(ms)**：深い眠り。より多くの回路を止め、**リセットとして**目覚めます（10.1 のとおり）。長い眠りはこちら

本書の主役は deepsleep 一択です。10分の眠りに状態保持は要りませんし、4mA の差は10分間ずっと効き続けるので、電池寿命に直結します。

ここで正直な告白をひとつ。RP2350 というチップ自体は、データシート上 µA 級の超低消費モード（dormant）を持っています。しかし MicroPython の `deepsleep` はそこまで深く潜らず、**6mA が現実の床**でした。「カタログの数字」と「自分のソフトウェアスタックで出る数字」は別物 — だから実測するのです。この床を破る手段は10.7に残してあります。

もうひとつ実務上の注意。**スリープ中の Pico はシリアルにも応答しません。** USB 越しに様子を見ようとしても沈黙が返るだけで、故障と紛らわしい（筆者も最初ぎょっとしました）。スリープを含むプログラムのデバッグは、10.1 の脱出ハッチとLED、そして次節以降の電流計が頼りになります。

## 10.3 Wi-Fi チップの消し忘れ — lightsleep を帳消しにする 29mA の罠

この章でいちばん高くつく罠を、実測ストーリーでお見せします。

筆者が最初にスリープ電流を測ったときのことです。Wi-Fi のテストを済ませたあと、続けて lightsleep 中の電流を測ると — **29.2mA**。アイドル（17.7mA）より**高い**のです。眠っているのに、起きているときより電気を食う。明らかにおかしい。

犯人は第3章で予告した「別の住人」でした。Wi-Fi チップ CYW43439 は RP2350 とは独立した存在なので、**本体がどれだけ深く眠っても、自分から寝てはくれません**。直前のテストで起こした Wi-Fi チップが、スリープ中もずっと通電状態で残っていたのです。

対策はたった1行です。

```python
wlan.active(False)    # CYW43439 を明示的に消灯する
```

これを入れて測り直すと、lightsleep は 29.2mA → **10.1mA**。1行で電流が3分の1、つまり**電池寿命が3倍**変わりました。本書の全実測のなかで、これが最も費用対効果の高い1行です。

```text
  lightsleep の実測:
  Wi-Fi 消し忘れ   ████████████████████████████ 29.2mA  ← アイドルより悪い!
  active(False)後  ██████████ 10.1mA
```

深く刻んでください：**スリープ前の儀式は「wlan.active(False)」から。** 10.5 で作る通知関数は、この儀式を関数の中に閉じ込めて、忘れられない構造にします。

## 10.4 OV7670 の電源管理 — カメラも眠らせる

本体と Wi-Fi を眠らせたら、残る起床者はカメラです。実測では、カメラ初期化後に XCLK（クロック供給）を止めるだけで約 **7.5mA** 下がることを確認しました（30.5mA → 23.0mA、動作中比）。PWM を止めるだけなので1行です：

```python
cam._pwm.deinit()     # XCLK停止。カメラは休止状態に
```

さらに攻める手が2段あります。

**PWDN ピン**（第4章の配線では GND 直結にしていた端子）を Pico の GPIO につなぎ替えれば、ソフトからカメラをパワーダウンモードに落とせます。**MOSFET でカメラの電源線ごと遮断**すれば、理論上カメラの消費はゼロになります（Nch MOSFET 1個と抵抗2本の定番回路 — 全回路図は付録 D）。

ただし、本書の main.py 構造では**そこまでの必要性は下がります**。deepsleep で本体がリセットされるとき XCLK の PWM も止まるため、カメラは自然に休止に落ちるからです。10分間欠の運用なら「XCLK 停止＋deepsleep」で実用になる、というのが筆者の判断です。PWDN/MOSFET は、撮影間隔を1時間・1日と伸ばして電池を数ヶ月持たせたい場合（10.7 の世界）に効いてくる装備だと位置づけてください。

## 10.5 Wi-Fi は「送るときだけ」— 接続時間を最小化する書き方

### 42mA の時間を1秒でも短く

Wi-Fi 動作中（接続処理・送信）の実測は **42.0mA** — 全状態の最高値です。とはいえ恐れる必要はありません。効くのは「電流×時間」なので、**時間を短くすればいい**のです。方針は3つ：

- つなぐのは通知があるときだけ（判定に変化がなければ Wi-Fi は一切触らない）
- 送るのは最小限のテキスト（UDP で数十バイト。第1章の「8バイト対38,400バイト」の実践です）
- 送ったら即座に消灯（10.3 の儀式）

### notify.py — 儀式を閉じ込めた通知関数

```python
# notify.py — 「つなぐ→送る→必ず消す」を1関数に閉じ込める
import network, socket, time
import wifi_config                     # SSID/PSK は別ファイルに (コラム参照)

def send_udp(message, timeout_s=15):
    wlan = network.WLAN(network.STA_IF)
    try:
        wlan.active(True)
        wlan.connect(wifi_config.SSID, wifi_config.PSK)
        for _ in range(timeout_s * 10):          # 接続待ち (0.1秒刻み)
            if wlan.isconnected():
                break
            time.sleep_ms(100)
        else:
            return False                          # 接続失敗。今回は諦める
        s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        s.sendto(message.encode(), (wifi_config.DEST, wifi_config.PORT))
        s.close()
        return True
    finally:
        wlan.active(False)                        # ★成功でも失敗でも必ず消灯
```

設計意図は2つ。**`finally` で消灯を保証する**こと — 接続に失敗しようが例外が飛ぼうが、この関数を通る限り 29mA の罠にはまりません。そして**失敗したら諦める**こと — 間欠動作カメラは10分後にまた起きます。その場でしつこく再試行して電池を溶かすより、次のサイクルに任せる方が合理的です。

筆者の実測では、接続確立に数秒〜十数秒、送信自体は一瞬でした。1回の通知はおおむね「42mA × 10秒」— 電池換算で 0.12mAh、単3×2本の**1万7千分の1**です。通知そのものは、驚くほど安い。

受け側（スマホへの通知方法）はいくつか選択肢があり、第11章のプロジェクト1で LAN 内の通知サーバ経由で仕上げます。

### コラム：Wi-Fi のパスワードをコードに書かない

SSID とパスワードは main.py に直書きせず、`wifi_config.py` という別ファイルに分けています。コードを Git や書籍サポートサイトで共有するとき、認証情報だけ共有から外せるようにするためです。**「コードは公開できる、設定は公開しない」の線引きをファイルの境界に一致させる** — 小さな習慣ですが、事故を確実に防ぎます。

## 10.6 消費電流の実測方法と、電池寿命の計算

### 測り方 — 目視の電流計で十分戦える

本章の実測は、特別な計測器なしで取れます。筆者の方法：

- **計器**：USB 電流計（手軽だが分解能 10mA 程度の製品が多い）または mA レンジのあるテスターを電源線に直列に。スリープ電流まで読むなら後者
- **測る対象**：瞬間のピークではなく「**状態ごとの定常値**」。撮影中・スリープ中・Wi-Fi 中…と、装置の状態を1つに固定して、表示が落ち着いたら読む
- **状態の固定**：各状態を無限に保持する小さなテストスクリプトを用意します（サポートリポジトリ `code/integrated/v3_states.py`。「推論し続けるだけ」「Wi-Fi 送信し続けるだけ」といった関数の詰め合わせです）
- **スリープの測定だけは特別**：スリープ中はシリアルが死ぬので、PC から操作できません。「20秒起きて30秒眠る」を自動で繰り返す main.py を仕込み、装置に勝手にやらせて表示を読みます

ピークの波形が見たくなったら、それは USB 電流計の卒業時期です。とはいえ電池寿命の見積もりには定常値で十分 — 理由は次の算数が示します。

### 電池寿命の算数 — 全実測値を1つの数字に

第3章の式に、この章で取った値を全部代入します。運用条件は「撮影間隔10分、変化があったときだけ通知」。1サイクル（600秒）の内訳：

| 工程 | 時間 | 電流 | 電荷 (mA・秒) |
|---|---|---|---|
| 起動＋撮影＋推論 | 約2秒 | 30.5 mA | 61 |
| 通知（変化があった回のみ） | 約6秒 | 42.0 mA | 252 |
| deepsleep | 残り約592秒 | 6.0 mA | 3,552 |
| **合計** | 600秒 | — | **約3,865** |

```text
  平均電流 = 3,865 mA・秒 ÷ 600秒 ≒ 6.4 mA
  電池寿命 = 2000 mAh ÷ 6.4 mA ≒ 310時間 ≒ 13日
```

**単3電池2本で約13日** — 第1章の「2週間」の正体がこの計算です。しかもこれは毎サイクル通知が飛ぶ悲観側の見積もりで、実際の置き配検知なら通知は日に数回。さらに測定は USB 給電経路込みの上限側です。実運用は計算より長持ちする方向にしか転びません。

表をもう一度見てください。600秒のうち、**電荷の92%は deepsleep の 6.0mA が占めています**。撮影や通知をどれだけ削っても焼け石に水で、効くのはスリープの床を下げることだけ — 序盤から繰り返してきた「電池寿命は眠りの深さで決まる」の、これが最終的な数字です。

そしてこの結論が、最後の節への扉になります。**6.0mA の床を破れたら、何が起きるのか？**

## 10.7 さらに攻める — 外部タイマー IC（TPL5110）による電源断スリープ

### 究極のスリープは「死んでいる」こと

MicroPython の deepsleep が 6mA で頭打ちなら、発想を変えます。**眠るのをやめて、電源ごと切ってしまえばいい。** ただし自分では再起動できないので、目覚まし役を外部に置きます。

それが **TPL5110** という数百円のタイマー IC です。役割はただひとつ：設定した間隔（抵抗値で 100ms〜2時間を選択）で電源スイッチを ON にし、機器から「仕事終わった」の合図（DONE 信号）を受けたら電源を切って、次の時刻まで待つ。

```text
   電池 ──→ [TPL5110] ──電源──→ [Pico + カメラ]
              ↑    │                  │
              │    └── 10分ごとにON     │
              └────── DONE 信号 ←──────┘ (main.py の最後で1本のGPIOをHIGHに)
```

main.py の変更は、最後の1行 `machine.deepsleep(...)` を「DONE ピンを HIGH にする」に差し替えるだけです。リセットから始まる本書の main.py 構造は、**電源断から始まる TPL5110 方式とそのまま互換** — 10.1 でこの設計様式を選んだ伏線が、ここで完全に回収されます。

### 数字はどう変わるか

TPL5110 の待機電流は**約35µA（0.035mA）**。deepsleep の 6mA の、実に170分の1です。同じ算数をやり直すと：

```text
  平均電流 ≒ 0.035 + 0.5(活動分) ≒ 0.5 mA
  電池寿命 = 2000 mAh ÷ 0.5 mA ≒ 4000時間 ≒ 半年近く
```

スリープが完全に消えた結果、今度は**活動時間（撮影と通知）が家計の主役**に躍り出ます。ここまで来ると 10.4 の PWDN/MOSFET や起動時間の短縮が意味を持ち始める — 省電力設計は、床を1枚破るたびに新しい最適化が始まる、奥の深いゲームです。

トレードオフも明記しておきます。部品と配線が増えること。間隔の変更が「コード1行」から「抵抗の交換」になること。そして毎回完全なコールドブートなので、起動時間（1〜2秒）が相対的に重くなること。**まず deepsleep 方式（13日）で運用を確立し、長期運用の必要が見えたら TPL5110 に進む** — 本書はこの二段構えをおすすめします。
