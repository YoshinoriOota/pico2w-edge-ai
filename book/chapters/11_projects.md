# 第11章 応用プロジェクト — 作った装置を暮らしに置く

部品はすべてそろいました。カメラ（第4章）、モデル（第6〜8章）、推論（第9章）、電池運用（第10章）。この章では、それらを3つの実用プロジェクトに組み上げます。プロジェクト1（置き配検知）は手順を最初から最後まで通しで、プロジェクト2・3はプロジェクト1からの差分として書きます。

## 11.1 プロジェクト1：置き配検知カメラ — 本書の集大成

### 完成までのロードマップ

第1章の風景を、章番号つきの工程表にします。

```text
  ① 配線した Pico を玄関の設置場所に仮固定する        (第4章の配線のまま)
  ② その場所・その画角でデータを収集する              (第7章: 各クラス100枚〜)
  ③ NNC で学習し、混同行列を確認する                 (第6章の手順)
  ④ NNB をエクスポートして Pico にコピーする          (第8章: 右クリック3回)
  ⑤ Pico に一式を配置し、main.py を仕込む            (この節)
  ⑥ 通知の受け皿を常駐マシンで動かす                  (この節)
  ⑦ USB で1サイクルの動作を確認 → 電池に切り替えて設置  (この節)
```

大事なのは①が最初に来ることです。第7章の鉄則「本番と同じカメラ・同じ位置・同じ画角で撮る」— 設置場所を決めてからデータを撮る。逆にすると全部やり直しになります。

### ⑤ Pico への配置 — ファイル一覧

最終形で Pico のフラッシュに置くファイルは7つです（すべてサポートリポジトリにあります）。

| ファイル | 役割 | 由来 |
|---|---|---|
| `main.py` | 間欠動作サイクル本体 | 第10章の骨格の完全版 |
| `ov7670.py` | カメラドライバ | 第4章 |
| `dnnrt_loader.py` | モデル読み込み補助 | 第9章 |
| `preprocess.py` | 前処理（収集ツールと同一ロジック） | 第9章 |
| `notify.py` | Wi-Fi 通知（つなぐ→送る→必ず消す） | 第10章 |
| `wifi_config.py` | SSID/PSK/宛先（**これだけ手書き**） | 第10章のコラム |
| `model.nnb` | あなたの学習済みモデル | 第8章 |

`main.py` の冒頭にある設定3行だけ、自分の環境に合わせます。

```python
CLASSES = ["box", "empty"]   # make_nnc_dataset.py が表示した割り当て表のとおりに
NOTIFY_CLASS = 0             # どのクラスへの変化で通知するか
THRESHOLD = 0.8              # これ未満の確度は「判定保留」(11.4で調整)
```

### ⑥ 通知の受け皿 — notify_server.py

通知の受け側は、常時起きているマシン（デスクトップ PC、ラズパイ、NAS など）で小さな UDP サーバを動かすだけです。

```sh
python notify_server.py            # ポート9999で待ち受け、受信を表示&ログ保存
```

受信したら時刻付きでログに残す、20行ほどのスクリプトです（サポートリポジトリ `code/integrated/pc/`）。スマホへのプッシュ通知に育てたい場合は、このサーバから先を LINE Notify 系のサービスや ntfy などに中継するのが定石です — 受け皿を1枚挟んでおくと、通知先の流行り廃りに Pico 側が振り回されません。

### ⑦ 動作確認 — そして「通知が届かない」の診察室

USB につないだまま、Thonny で main.py を実行して1サイクルの動作を見ます（脱出ハッチの5秒を過ぎると自動で走ります）。カメラの前に箱を置いて、受け皿のログに1行増えれば合格。電池に切り替えて、設置完了です。

…と、さらっと書きましたが、**この⑦の Wi-Fi 通知こそ本書の全工程でいちばん「見えない敵」が多い場所**です。筆者自身、この章の検証で立て続けに2つの罠を踏みました。実話ベースの診察室として残しておきます。

**症状：`send_udp` が False を返す（接続に失敗する）**

真っ先に疑うべきは **SSID の 5GHz/2.4GHz 問題**です。筆者のルーターは「〜-a」（5GHz）と「〜-bg」（2.4GHz）の2つの SSID を出しており、うっかり 5GHz 側を `wifi_config.py` に書いていました。Pico 2 W は 2.4GHz 専用（第3章）なので、**5GHz の SSID は永遠に見つかりません**。切り分けは Pico にスキャンさせるのが確実です：

```python
>>> import network
>>> wlan = network.WLAN(network.STA_IF); wlan.active(True)
>>> [s[0] for s in wlan.scan()]      # Pico から「見えている」SSID の一覧
[b'HG8045-XXXX-bg']                  # ← 2.4GHz しか見えない。これが正解の接続先
```

**症状：`send_udp` は True なのに、受け皿に何も届かない**

これが本命の難敵でした。Pico は「送った」と言い、受け側は「来ない」と言う。ファイアウォール？ ルーターの分離機能？ — 筆者もそう疑って回り道をしましたが、真犯人は自分のコードでした。

`sendto()` は「送信キューへの受付」であって、パケットが実際に電波になるまでには数十ミリ秒かかります。**その前に `wlan.active(False)` で Wi-Fi チップを消灯すると、キューに載ったままのパケットごと闇に葬られる**のです。エラーはどこにも出ません。対策は、送信後にひと呼吸置くこと：

```python
s.sendto(...)
time.sleep_ms(300)     # パケットが電波になるのを待ってから
wlan.active(False)     # 消灯する
```

本書の `notify.py` は修正済みですが、この2つ —「**電波の帯が違う**」と「**送った気になって電源を切る**」— は無線マイコン全般で再演される古典です。ログに何も出ない不具合ほど、疑う順番が物を言います：Pico のスキャン結果 → 送信後の待ち → 受け側マシンのファイアウォール → ルーターの分離機能、の順で。

なお筆者の環境では、この2つを直した結果、**撮影→推論→通知→受け皿のログ着信**までの一気通貫が安定して動きました（Wi-Fi 接続込みで1通知あたり約5.5秒）。

## 11.2 プロジェクト2：観察カメラ — 「変化」を記録する長期観察機

### 通知ではなく記録を残す

2つ目は応用のひねりです。ベランダの鉢植えの開花、庭に来る野鳥、水槽の様子 — 「変化した瞬間の**画像そのもの**を残したい」という用途に、置き配カメラを転用します。

構成の差分は main.py だけです。「変化を検知したら通知」を「変化を検知したら**フレームを保存**」に置き換えます：

```python
    if best != prev:
        fname = "log_%04d_%s.raw" % (counter(), CLASSES[best])
        with open(fname, "wb") as f:
            f.write(frame)               # 38,400バイトの生フレームを保存
        write_last_state(best)
```

Wi-Fi を一切使わないので、電池はさらに長持ちします（10.6 の算数で平均約 6.1mA → **約2週間**）。画像の回収は、様子を見に行ったときに USB をつないで `mpremote cp` でまとめて（第4章の convert_frame.py で PNG 化できます）。

### 容量の算数

フラッシュ 4MB のうち、ファームウェア等を除いた空きが約 3MB。1フレーム 38,400 バイトなので、**約80枚**の変化イベントを保存できます。「開花の瞬間」のような低頻度イベントなら数ヶ月ぶんです。撮影間隔と電池・容量の関係は、10.6 の式にあなたの想定を入れて見積もってください — この「自分の運用条件で電卓を叩ける」ことこそ、第10章を通った読者の武器です。

## 11.3 プロジェクト3：電池＋ソーラーでの連続運用

### 「充電される速度 > 消費する速度」にする

単3×2本で13日 — 十分実用的ですが、電池交換自体をなくす最終形態がソーラー運用です。成立条件は収支の1行に尽きます：

```text
  1日の消費   : 平均6.4mA × 24h ≒ 154mAh
  1日の充電   : 2W級パネル(実効300mA前後) × 実効日照2〜3時間 ≒ 600〜900mAh
  → 晴れの日1日で、雨の4〜5日分を稼げる収支
```

構成は「小型ソーラーパネル → 充電モジュール（TP4056 など）→ リチウムイオン電池 → Pico の VSYS」が定番です。Pico の VSYS は 1.8〜5.5V を受け付けるので、リチウムイオン電池（3.0〜4.2V）を直結できるのが楽なところです。

注意点は3つ。**冬と連続悪天候**（上の収支は夏の皮算用です。パネルは余裕を持って大きめに）、**電池の保護**（保護回路つきのセルか充電モジュールを選ぶ。屋外の高温にも注意）、そして**防水**（電子工作の常で、ケースの工夫が本体より時間を食います）。ここから先は電源工作の領域なので、本書は入口の紹介にとどめます — が、10.7 の TPL5110 と組み合わせた「メンテナンスフリーの数年運用」はロマンがあります。挑戦する読者はぜひ実運用データをブログ等で公開してください。

## 11.4 改造のヒント — 精度と付き合い続ける

設置したカメラは「完成」ではなく「運用の開始」です。育て方の定石を4つ。

### 閾値（THRESHOLD）のチューニング

main.py の判定保留閾値 0.8 は保守的な初期値です。誤通知が多いなら上げる、見逃しが多いなら下げる。判断材料は**実運用のログ**です — notify_server のログに確度も記録されているので、「誤検知したときの確度はいくつだったか」を見てから動かします。勘で回すダイヤルではありません。

### 「不明」画像こそ宝

確度が閾値未満だった（判定保留になった）フレームは、**モデルが苦手としている実例**です。プロジェクト2の要領でこれを保存しておき、正しいラベルを付けて学習データに追加 → 再学習 → model.nnb を差し替え。この「現場の失敗を教材に変えるループ」を2〜3周すると、精度は目に見えて安定します。モデル差し替えがファイルコピー1回（第9章）である恩恵を、ここで最大限に使ってください。

### クラスの追加

「荷物あり/なし」に「人がいる」を足したくなったら：③クラスのフォルダを作って収集（第7章）→ NNC で最後の Affine の出口を 3 に変えて再学習（第6章）→ エクスポートして差し替え（第8章）→ main.py の `CLASSES` を3要素に。全工程が既習事項の再演です。ただし第6章の教訓を忘れずに — 追加するクラスは、既存クラスと**シルエットで区別できるもの**を。

### 撮影間隔のチューニング

最後に、運用の性格を決める一番太いダイヤルです。10.6 の算数から抜粋します。

| 間隔 | 平均電流（概算） | 単3×2本での寿命 | 向く用途 |
|---|---|---|---|
| 2分 | 約7.6mA | 約11日 | 在席検知など即時性重視 |
| 10分 | 約6.4mA | **約13日** | 置き配検知（本書標準） |
| 60分 | 約6.1mA | 約14日 | 観察カメラ |

表が語る意外な真実：**deepsleep が 6mA を食い続ける限り、間隔を延ばしても寿命はほとんど伸びません**。2分間隔ですら11日動く、とも読めます（即時性はかなり贅沢できる）。一方、間隔を延ばして劇的に効かせたいなら、床そのものを下げる TPL5110（10.7）の出番です — 60分間隔なら平均 0.1mA を切り、理論上は**電池の自己放電と競争する世界**に入ります。
